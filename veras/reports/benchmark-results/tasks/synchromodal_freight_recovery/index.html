# Synchromodal Freight Recovery

A logistics service provider must plan container movements across a multimodal
freight corridor. Customers provide origin, destination, cargo type, release
time, delivery promise, and container volume. The provider can reject some
orders at a penalty, but accepted orders must have an advance reservation plan
and a valid recourse plan for every disruption scenario.

You are helping a logistics service provider protect a three-day container
transport plan on a Rhine-Alpine style corridor. The company sells modal-free
delivery promises to shippers, then chooses a mix of inland waterway, rail, and
truck services before the week starts. After disruptions are revealed, the
dispatcher may re-plan each accepted shipment across the remaining scheduled
services and spot truck capacity.

## Planning Goal

Minimize the total policy cost. The cost includes:

- rejection penalties for orders not served,
- advance reservation costs for booked scheduled services,
- scenario operating costs for actually used services,
- extra spot-market costs when a scenario plan uses lanes not reserved for that
  order,
- transfer handling costs at intermediate terminals,
- lateness penalties after the promised due time,
- activation and under-use charges for contracted operator-day slots,
- carbon penalties when scenario emissions exceed the configured allowance, and
- a tail-risk charge based on the most expensive disruption outcomes.

## Hard Planning Rules

Every order must be either rejected or accepted. Rejected orders must have no
reserved path and no scenario plans. Accepted orders must have exactly one
reserved path and one recourse path for every listed scenario.

Each path must start at the order origin, end at the order destination, and use
only scheduled lanes from `lanes.csv`. Consecutive lanes must connect at the
same terminal and respect that terminal's minimum transfer time. The first lane
must depart no earlier than the order release time. A delivered order may arrive
late, but not beyond the published maximum lateness tolerance.

Advance reservations consume each lane's published booking allowance. Scenario
recourse plans consume the usable disrupted capacity of every selected lane.
That usable capacity starts from the normal physical allowance and incorporates
the applicable disruption adjustment; a cancelled lane has no usable capacity.

The provider has operator-day slot contracts for rail and inland-waterway
partners. When any accepted order reserves capacity on a contracted operator's
services for a day, the plan pays that contract's activation charge and is
measured against the listed minimum booking quantity. Booking below the minimum
is allowed but pays the listed under-use charge; booking above the maximum is
not allowed. Contract days are determined by the nominal departure day of each
reserved lane.

Terminal throughput is limited by `scenario_terminal_limits.csv`. Origin loading
and every intermediate transfer count against the applicable scenario-day
throughput allowance. Arrival at the final destination does not create another
outbound handling move.

Some scenario-terminal-day combinations also have ordinary specialty-resource
limits in `terminal_resource_limits.csv`. Refrigerated orders consume
reefer-plug TEU at the origin loading terminal and every intermediate transfer
terminal. Hazmat orders consume hazmat-inspection TEU at those same handling
events. Exceeding the listed ordinary capacity is allowed only by paying the
listed emergency overflow cost. Missing rows mean no additional
specialty-resource charge beyond the normal terminal throughput and
compatibility rules.

Cargo compatibility matters. Refrigerated orders may only use lanes and
transfer terminals that support reefer handling. Hazmat orders may only use
lanes and terminals that allow hazmat containers. A path may not use more
transfers than the order allows.

Customer-service commitments apply across accepted orders. For each priority
class listed in `service_requirements.csv`, the accepted TEU must meet the
minimum listed value. Rejections are still allowed, but they must respect these
portfolio-level service floors.

The provider has a modal-shift commitment. Across accepted TEU, both the advance
reservation plan and every scenario plan must keep at least the configured share
of TEU on rail or inland-waterway lanes. Emergency all-road recovery is allowed
only when the rest of the plan still meets this commitment.

## Data Dictionary

`config.json` gives global settings for risk treatment, lateness tolerance,
emissions policy, and modal-shift commitments.

`orders.csv` lists shipment requests. Times are minutes from the beginning of
the planning horizon, and each request includes its volume, service promise,
cargo requirements, rejection penalty, lateness economics, and priority class.

`terminals.csv` lists terminal capabilities. The `timezone_group` field is only
descriptive; all times are already normalized to one clock.

`lanes.csv` lists scheduled services, including their nominal timing,
reservation allowance, physical scenario capacity, operating economics,
emissions, and cargo-handling compatibility.

`operator_contracts.csv` lists daily reservation commitments by service
operator. The minimum is a paid-use commitment once the operator-day is active;
the maximum is a hard reservation cap.

`service_requirements.csv` lists portfolio-level accepted-volume commitments by
order priority class.

`transfer_rules.csv` gives handling time and cost for transfers at each
terminal, with cargo-specific handling increments.

`scenarios.csv` gives scenario probabilities and short descriptions.

`scenario_lane_adjustments.csv` gives scenario-specific changes to service
availability, timing, and spot recovery costs. Missing lane/scenario pairs use
the nominal service values with no delay.

`scenario_terminal_limits.csv` gives terminal-day throughput limits for each
scenario.

`terminal_resource_limits.csv` gives scenario-day ordinary capacities and
overflow costs for special handling resources such as reefer plugs and hazmat
inspection slots.

## Modeling choices

The instance is small enough to enumerate feasible shipment paths. I therefore use
a path-based two-stage stochastic mixed-integer model:

- first-stage binary variables choose whether to accept each order and which
  nominal reserved path to book;
- second-stage binary variables choose one recourse path for each accepted
  order in each public scenario;
- paired first-stage/second-stage binaries are used so that the benchmark's
  order-specific "unreserved lane" recovery premium is priced exactly.

This is stronger and simpler than a lane-by-lane flow model because path
feasibility with release times, transfer times, cargo compatibility, transfer
limits, and lateness tolerance is handled during preprocessing.

## Planning Goal

Minimize the total policy cost. The cost includes:

- rejection penalties for orders not served,
- advance reservation costs for booked scheduled services,
- scenario operating costs for actually used services,
- extra spot-market costs when a scenario plan uses lanes not reserved for that
  order,
- transfer handling costs at intermediate terminals,
- lateness penalties after the promised due time,
- activation and under-use charges for contracted operator-day slots,
- carbon penalties when scenario emissions exceed the configured allowance, and
- a tail-risk charge based on the most expensive disruption outcomes.

## Hard Planning Rules

Every order must be either rejected or accepted. Rejected orders must have no
reserved path and no scenario plans. Accepted orders must have exactly one
reserved path and one recourse path for every listed scenario.

Each path must start at the order origin, end at the order destination, and use
only scheduled lanes from `lanes.csv`. Consecutive lanes must connect at the
same terminal and respect that terminal's minimum transfer time. The first lane
must depart no earlier than the order release time. A delivered order may arrive
late, but not beyond the published maximum lateness tolerance.

Advance reservations consume each lane's published booking allowance. Scenario
recourse plans consume the usable disrupted capacity of every selected lane.
That usable capacity starts from the normal physical allowance and incorporates
the applicable disruption adjustment; a cancelled lane has no usable capacity.

The provider has operator-day slot contracts for rail and inland-waterway
partners. When any accepted order reserves capacity on a contracted operator's
services for a day, the plan pays that contract's activation charge and is
measured against the listed minimum booking quantity. Booking below the minimum
is allowed but pays the listed under-use charge; booking above the maximum is
not allowed. Contract days are determined by the nominal departure day of each
reserved lane.

Terminal throughput is limited by `scenario_terminal_limits.csv`. Origin loading
and every intermediate transfer count against the applicable scenario-day
throughput allowance. Arrival at the final destination does not create another
outbound handling move.

Some scenario-terminal-day combinations also have ordinary specialty-resource
limits in `terminal_resource_limits.csv`. Refrigerated orders consume
reefer-plug TEU at the origin loading terminal and every intermediate transfer
terminal. Hazmat orders consume hazmat-inspection TEU at those same handling
events. Exceeding the listed ordinary capacity is allowed only by paying the
listed emergency overflow cost. Missing rows mean no additional
specialty-resource charge beyond the normal terminal throughput and
compatibility rules.

Cargo compatibility matters. Refrigerated orders may only use lanes and
transfer terminals that support reefer handling. Hazmat orders may only use
lanes and terminals that allow hazmat containers. A path may not use more
transfers than the order allows.

Customer-service commitments apply across accepted orders. For each priority
class listed in `service_requirements.csv`, the accepted TEU must meet the
minimum listed value. Rejections are still allowed, but they must respect these
portfolio-level service floors.

The provider has a modal-shift commitment. Across accepted TEU, both the advance
reservation plan and every scenario plan must keep at least the configured share
of TEU on rail or inland-waterway lanes. Emergency all-road recovery is allowed
only when the rest of the plan still meets this commitment.

# Optimization Modeling Core

## Use when

- The user gives a word problem, business process, paper scenario, or benchmark prompt and expects a formal optimization model.
- Solver code exists but the issue appears to be a missing or incorrect formulation.
- The task asks for a complete model, not only a heuristic, simulation, or data summary.

## Do not use when

- The task is purely about software plumbing, visualization, data cleaning, or report writing.
- The problem is already fully formulated and the user only asks for code translation into a specific solver; use the solver-specific skill as the primary guide.
- The request is exploratory and the user explicitly wants brainstorming without implementation.

## Model-first workflow

1. Restate the business decision in plain language.
2. Identify sets, indices, units, and time granularity.
3. Extract parameters from data files and confirm units.
4. Define decision variables with domains and business meaning.
5. Write the objective with every cost, reward, penalty, and service term.
6. Write constraints grouped by operational rule.
7. Check edge cases: missing eligibility, impossible demand, fixed commitments, and terminal-state requirements.
8. Only then implement code.

## Ambiguity handling

- If the brief is ambiguous but data and examples imply a convention, state the assumption and continue.
- If ambiguity changes feasibility, objective direction, or deliverable schema, ask before coding or implement the least risky interpretation with a clear note.
- If units conflict across files, normalize units explicitly before modeling.
- If a hard requirement conflicts with data, diagnose the conflict before adding slack variables.

## Formulation checklist

- Every row in an input table should either become a parameter, an eligibility rule, or be explicitly irrelevant.
- Every decision variable should appear in at least one binding constraint and usually in the objective.
- Demand balance should use the correct equality or inequality direction; do not weaken equality to `>=` unless surplus is genuinely allowed.
- Capacity constraints should include activation/open/setup binaries when the business says inactive resources cannot produce, ship, or serve.
- Shortage, backlog, overtime, outsourcing, and postponement variables need explicit cost and bounds.
- Multi-period models need state transition equations and initial/terminal states.
- If the user asks for explanation, describe the modeling logic in business terms after solving.

## Constraint boundary rules

- Hard constraints represent physical impossibility, policy mandates, legal requirements, or explicit benchmark feasibility rules.
- Soft constraints need penalty variables or objective terms; do not silently turn hard constraints into penalties.
- Service levels should specify numerator, denominator, eligible population, and time window.
- Fairness constraints should define the comparison group and whether unavailable resources count.
- Logical implications need both directions only when the business rule says equivalence, not merely implication.

## Objective boundary rules

- Confirm whether the problem minimizes cost, maximizes profit, maximizes service, or uses lexicographic priorities.
- Do not mix penalties with primary economics unless their scale is intentional.
- Include fixed costs only once per activated entity.
- Include revenue only for fulfilled demand or accepted jobs, not for unmet or canceled work.
- Keep reporting metrics separate from optimized objective terms unless the prompt explicitly optimizes them.

## Implementation expectations

- Use structured parsing for CSV/JSON instead of manual string manipulation.
- Keep solver code, solution export, and validation code clearly separated.
- For benchmark or task environments, read the provided brief before coding and follow the expected output schema exactly.
- When comparing two answers, diagnose concrete formulation differences and objective consequences, not only feasibility.
- Write exported solutions at the precision expected by the checker; avoid unnecessary rounding.
- Preserve the input schema and output schema unless the user asks to redesign the benchmark.

## Verification boundary

- Verify feasibility independently from solver status when an evaluator or checker exists.
- Recompute objective from exported artifacts, not only from in-memory solver expressions.
- For benchmark tasks, create at least one negative check for each newly added rule when practical.
- For paper or real-world tasks, separate what is directly supported by the source from synthetic or assumed data.

## Red flags

- Objective terms that are counted twice or charged at the wrong marginal rate.
- Binary variables not linked tightly enough to continuous activity.
- Time periods shifted by one index.
- Average or fairness constraints that ignore the denominator or eligibility set.
- Public prompt files that reveal solver-ready variables or formulas when the benchmark is meant to test modeling translation.
- A feasible solution that exploits missing eligibility, free disposal, negative cycles, or unbounded production.
- A model that reports optimality after a time limit, infeasible status, or missing incumbent.

# Advanced MIP Patterns

## Use when

- The formulation needs logical implications, fixed charges, activation decisions, ordering, no-overlap, disjunctions, min/max, absolute values, tiers, route state, or resource calendars.
- A simple LP/MIP is producing unrealistic behavior because decisions are not linked tightly enough.
- The model is slow or infeasible and the likely cause is weak big-M logic, excessive pairwise variables, or missing state transitions.

## Do not use when

- A continuous LP is sufficient and adding binaries would not represent a real decision.
- The task is better handled by a specialized CP-SAT, constraint programming, nonlinear, or simulation method and the user did not require MIP.
- The user only needs a high-level explanation; do not introduce advanced constructs unless they clarify the actual model.

## General boundary rules

- Add binaries only for real yes/no choices, disjunctions, or nonconvex structure.
- Prefer the tightest formulation that matches the business rule; avoid decorative binaries.
- Use solver-native constructs when they improve clarity and are supported by the target environment.
- If a construct makes the model much slower, compare it with a simpler valid alternative before keeping it.

## Fixed charge and activation

- Use a binary `y` for whether an activity/resource is active.
- Link activity with a tight bound: `x <= U * y`.
- Add lower activation only when the business requires minimum use: `x >= L * y`.
- Charge fixed cost once through `fixed_cost * y`, not per unit.
- Do not force `y = 1` whenever `x = 0` unless the activity is mandatory.
- If there are startup/shutdown costs over time, separate active state from transition state.

## Logical rules

- Prefer solver-native indicator constraints for simple if-then rules when they keep the model clearer.
- If using big-M, derive M from data bounds and keep one M per rule family when possible.
- For either-or choices, use binaries whose sum is exactly one or at most one, matching the business rule.
- Distinguish implication (`A -> B`) from equivalence (`A <-> B`); the reverse direction often needs a separate constraint.
- For conditional capacity, link both activity and resource use to the condition.

## Min, max, absolute value

- For `z = max(a, b)`, add `z >= a`, `z >= b`, and objective pressure if minimizing z. Use binaries only when equality is needed without objective pressure.
- For absolute deviation `d = |x - target|`, add `d >= x - target` and `d >= target - x`.
- For service-level penalties, separate hard feasibility from soft penalty variables.
- For `min`, either transform with signs or add binaries when equality is not enforced by the objective.
- For ratio constraints, cross-multiply only when denominators are constant or safely bounded away from zero.

## Sequencing and no-overlap

- For jobs sharing a resource, use order binary `before[i,j]`.
- Typical pattern:
  - `start[j] >= end[i] - M * (1 - before[i,j])`
  - `start[i] >= end[j] - M * before[i,j]`
- Compute M from the scheduling horizon, not from an arbitrary large number.
- Include setup, cleanup, travel, rest, or turnover time in the correct side of the ordering constraint.
- Create pairwise order variables only for pairs that can share a resource or conflict.
- If time is discrete and the horizon is small, a time-indexed model may be cleaner than pairwise disjunctions.

## Piecewise and tiers

- Use solver-native piecewise-linear features for convex piecewise costs when suitable.
- For nonconvex tiers, use explicit segment variables and segment activation binaries.
- Ensure tier quantities sum to the original activity and each tier has its own upper bound.
- Distinguish incremental tiers from all-units tiers; their formulations and costs differ.
- Check whether discount tiers create nonconvex incentives that require binary selection.

## State and inventory logic

- State variables need initial conditions, transition equations, and terminal requirements if the business specifies them.
- Route or schedule state should be advanced in event order, not checked only row by row.
- Recovery, restock, cleaning, cooldown, maintenance, and rest rules often require cumulative state or last-event logic.
- If state can reset, model the reset trigger and its resource/time cost.

## Debugging advanced models

- First solve a relaxed or smaller instance and inspect whether the intended binaries activate.
- Add named constraints so IIS output points to business rules.
- If the reference solution is infeasible, replay the relevant state transitions manually before changing the evaluator.
- If the LP relaxation is very weak, inspect big-M values, missing lower/upper links, and symmetry.
- If the model is unexpectedly infeasible, test each advanced rule family on a tiny instance with a known feasible solution.

# Synchromodal Freight Recovery Model

## Modeling choices

The instance is small enough to enumerate feasible shipment paths. I therefore use
a path-based two-stage stochastic mixed-integer model:

- first-stage binary variables choose whether to accept each order and which
  nominal reserved path to book;
- second-stage binary variables choose one recourse path for each accepted
  order in each public scenario;
- paired first-stage/second-stage binaries are used so that the benchmark's
  order-specific "unreserved lane" recovery premium is priced exactly.

This is stronger and simpler than a lane-by-lane flow model because path
feasibility with release times, transfer times, cargo compatibility, transfer
limits, and lateness tolerance is handled during preprocessing.

## Assumptions fixed from the public prompt

The prompt leaves a few costing details implicit. I use the least risky linear
interpretation consistent with the data:

1. The tail-risk term is a scenario-cost CVaR at confidence
   `alpha = tail_risk_alpha`, weighted in the objective by `tail_risk_weight`.
2. A scenario lane used by order `o` but not present in `o`'s reserved path
   pays, per TEU, the sum of:
   `spot_surcharge_per_teu` from `config.json`,
   `unreserved_lane_penalty_per_teu` from `config.json`, and
   the scenario-specific `spot_surcharge_per_teu` from

def lane_state(instance: dict, lane_id: str, scenario_id: Optional[str]) -> Optional[dict]:
    lane = instance["lane_by_id"][lane_id]
    if scenario_id is None:
        return {
            "depart_minute": lane["depart_minute"],
            "arrive_minute": lane["arrive_minute"],
            "capacity_teu": float(lane["scenario_capacity_teu"]),
            "spot_surcharge_per_teu": 0.0,
            "cancelled": 0,
        }
    adjustment = instance["scenario_lane_adjustments"].get(scenario_id, {}).get(lane_id)
    if adjustment and adjustment["cancelled"]:
        return None
    if adjustment:
        return {
            "depart_minute": lane["depart_minute"] + adjustment["departure_delay_minutes"],
            "arrive_minute": lane["arrive_minute"] + adjustment["arrival_delay_minutes"],
            "capacity_teu": float(adjustment["capacity_teu"]),
            "spot_surcharge_per_teu": float(adjustment["spot_surcharge_per_teu"]),
            "cancelled": 0,
        }
    return {
        "depart_minute": lane["depart_minute"],
        "arrive_minute": lane["arrive_minute"],
        "capacity_teu": float(lane["scenario_capacity_teu"]),
        "spot_surcharge_per_teu": 0.0,
        "cancelled": 0,
    }


def transfer_minutes(instance: dict, order: dict, terminal_id: str) -> int:
    rule = instance["transfer_rules"][terminal_id]
    minutes = rule["base_transfer_minutes"]
    if order["reefer"]:
        minutes += rule["reefer_extra_minutes"]
    if order["hazmat"]:
        minutes += rule["hazmat_extra_minutes"]
    return minutes


def lane_compatible(instance: dict, order: dict, lane: dict) -> bool:
    origin_terminal = instance["terminals"][lane["origin"]]
    destination_terminal = instance["terminals"][lane["destination"]]
    if order["reefer"]:
        if not lane["reefer_allowed"]:
            return False
        if not origin_terminal["reefer_supported"] or not destination_terminal["reefer_supported"]:
            return False
    if order["hazmat"]:
        if not lane["hazmat_allowed"]:
            return False
        if not origin_terminal["hazmat_allowed"] or not destination_terminal["hazmat_allowed"]:
            return False
    return True

def extract_solution(instance: dict, path_data: dict, model: Model, vars_data: dict) -> dict:
    if model.getNSols() <= 0 or model.getBestSol() is None:
        raise RuntimeError("SCIP finished without an incumbent; no solution can be exported.")
    sol = model.getBestSol()

    accepted_nominal = {}
    selected_pairs = {}
    for order in vars_data["feasible_orders"]:
        order_id = order["order_id"]
        chosen_nominal = None
        for nominal_path in path_data["nominal_paths"][order_id]:
            value = model.getSolVal(sol, vars_data["nominal_vars"][(order_id, nominal_path.index)])
            if value > 0.5:
                chosen_nominal = nominal_path
                break
        if chosen_nominal is not None:
            accepted_nominal[order_id] = chosen_nominal
            for scenario_id in instance["scenarios"]:
                chosen_scenario = None
                for scenario_path in path_data["scenario_paths"][(order_id, scenario_id)]:
                    key = (order_id, scenario_id, chosen_nominal.index, scenario_path.index)
                    value = model.getSolVal(sol, vars_data["pair_vars"][key])
                    if value > 0.5:
                        chosen_scenario = scenario_path
                        break
                if chosen_scenario is None:
                    raise RuntimeError(f"Missing scenario path for {order_id} in {scenario_id}")
                selected_pairs[(order_id, scenario_id)] = chosen_scenario

    orders_payload = []
    for order in instance["orders"]:
        order_id = order["order_id"]
        if order_id not in accepted_nominal:
            orders_payload.append(
                {
                    "order_id": order_id,
                    "accept": False,
                    "reserved_path": [],
                    "scenario_plans": [],
                }
            )
            continue
        scenario_plans = []
        for scenario_id in instance["scenarios"]:
            scenario_plans.append(
                {
                    "scenario_id": scenario_id,
                    "path": list(selected_pairs[(order_id, scenario_id)].lanes),
                }
            )
        orders_payload.append(
            {
                "order_id": order_id,
                "accept": True,
                "reserved_path": list(accepted_nominal[order_id].lanes),
                "scenario_plans": scenario_plans,
            }
        )

    return {"orders": orders_payload}


def compute_solution_metrics(instance: dict, path_data: dict, solution: dict) -> dict:
    order_entries = solution.get("orders", [])
    issues = []
    max_hard_residual = 0.0

    if len(order_entries) != len(instance["orders"]):
        issues.append("solution.json does not contain exactly one row per order")

    order_ids = [order["order_id"] for order in instance["orders"]]
    entry_map = {}
    for entry in order_entries:
        order_id = entry.get("order_id")
        if order_id in entry_map:
            issues.append(f"duplicate order_id {order_id} in solution")
            continue
        entry_map[order_id] = entry
    missing_orders = [order_id for order_id in order_ids if order_id not in entry_map]
    if missing_orders:
        issues.append(f"missing orders in solution: {missing_orders}")

    booking_usage = defaultdict(float)
    scenario_usage = defaultdict(float)
    throughput_usage = defaultdict(float)
    resource_usage = defaultdict(float)
    contract_usage = defaultdict(float)
    accepted_teu_by_priority = defaultdict(float)
    nominal_modal_expr = 0.0
    scenario_modal_expr = defaultdict(float)
    scenario_emissions = defaultdict(float)
    scenario_pair_cost = defaultdict(float)
    accepted_nominal = {}
    accepted_scenario = {}

    total_reject_cost = 0.0
    total_booking_cost = 0.0

    for order in instance["orders"]:
        order_id = order["order_id"]
        entry = entry_map.get(order_id)
        if entry is None:
            total_reject_cost += order["reject_penalty"]
            continue
        accept = bool(entry.get("accept"))
        reserved_path = tuple(entry.get("reserved_path", []))
        scenario_plans = entry.get("scenario_plans", [])

        if not accept:
            if reserved_path:
                issues.append(f"rejected order {order_id} has nonempty reserved_path")
            if scenario_plans:
                issues.append(f"rejected order {order_id} has nonempty scenario_plans")
            total_reject_cost += order["reject_penalty"]
            continue

        if order_id in path_data["forced_reject"]:
            issues.append(f"accepted order {order_id} has no feasible plan in all scenarios")

        nominal_path = path_data["nominal_lookup"].get((order_id, reserved_path))
        if nominal_path is None:
            issues.append(f"reserved_path for {order_id} is not a feasible nominal path")
            continue
        accepted_nominal[order_id] = nominal_path
        accepted_teu_by_priority[order["priority"]] += order["teu"]
        total_booking_cost += nominal_path.booking_cost
        nominal_modal_expr += nominal_path.nonroad_teu_legs - (
            instance["config"]["min_nonroad_teu_share"] * nominal_path.total_teu_legs
        )
        for lane_id in nominal_path.lanes:
            booking_usage[lane_id] += order["teu"]
            lane = instance["lane_by_id"][lane_id]
            contract_key = (lane["operator"], lane["day"])
            if contract_key in instance["contracts"]:
                contract_usage[contract_key] += order["teu"]

        if len(scenario_plans) != len(instance["scenarios"]):
            issues.append(f"accepted order {order_id} does not cover every scenario exactly once")
            continue
        seen_scenarios = set()
        for sp in scenario_plans:
            scenario_id = sp.get("scenario_id")
            if scenario_id not in instance["scenario_prob"]:
                issues.append(f"unknown scenario_id {scenario_id} for order {order_id}")
                continue
            if scenario_id in seen_scenarios:
                issues.append(f"duplicate scenario_id {scenario_id} for order {order_id}")
                continue
            seen_scenarios.add(scenario_id)
            lane_path = tuple(sp.get("path", []))
            scenario_path = path_data["scenario_lookup"].get((order_id, scenario_id, lane_path))
            if scenario_path is None:
                issues.append(
                    f"scenario path for order {order_id} in {scenario_id} is not feasible"
                )
                continue
            accepted_scenario[(order_id, scenario_id)] = scenario_path
            scenario_modal_expr[scenario_id] += scenario_path.nonroad_teu_legs - (
                instance["config"]["min_nonroad_teu_share"] * scenario_path.total_teu_legs
            )
            scenario_emissions[scenario_id] += scenario_path.emissions
            scenario_pair_cost[scenario_id] += scenario_path.base_pair_cost + pair_spot_cost(
                instance, order, nominal_path, scenario_path
            )
            for lane_id in scenario_path.lanes:
                scenario_usage[(scenario_id, lane_id)] += order["teu"]
            for handling_key, amount in scenario_path.handling.items():
                throughput_usage[(scenario_id, handling_key[0], handling_key[1])] += amount
            for resource_key, amount in scenario_path.resources.items():
                resource_usage[(scenario_id, resource_key[0], resource_key[1], resource_key[2])] += amount

    for lane in instance["lanes"]:
        used = booking_usage[lane["lane_id"]]
        excess = used - lane["booking_capacity_teu"]
        if excess > 1e-8:
            issues.append(
                f"booking capacity exceeded on {lane['lane_id']}: used {used:.8f}, cap {lane['booking_capacity_teu']:.8f}"
            )
        if lane["booking_capacity_teu"] > 0:
            max_hard_residual = max(max_hard_residual, excess / lane["booking_capacity_teu"])

    for scenario_id in instance["scenarios"]:
        for lane in instance["lanes"]:
            state = lane_state(instance, lane["lane_id"], scenario_id)
            cap = 0.0 if state is None else state["capacity_teu"]
            used = scenario_usage[(scenario_id, lane["lane_id"])]
            excess = used - cap
            if excess > 1e-8:
                issues.append(
                    f"scenario capacity exceeded on {scenario_id}/{lane['lane_id']}: used {used:.8f}, cap {cap:.8f}"
                )
            if cap > 0:
                max_hard_residual = max(max_hard_residual, excess / cap)

    for throughput_key, cap in instance["throughput_limits"].items():
        used = throughput_usage[throughput_key]
        excess = used - cap
        if excess > 1e-8:
            issues.append(
                f"throughput exceeded on {throughput_key}: used {used:.8f}, cap {cap:.8f}"
            )
        if cap > 0:
            max_hard_residual = max(max_hard_residual, excess / cap)

    for contract_key, contract_data in instance["contracts"].items():
        used = contract_usage[contract_key]
        excess = used - contract_data["max_booking_teu"]
        if excess > 1e-8:
            issues.append(
                f"contract max exceeded on {contract_key}: used {used:.8f}, max {contract_data['max_booking_teu']:.8f}"
            )
        if contract_data["max_booking_teu"] > 0:
            max_hard_residual = max(
                max_hard_residual, excess / contract_data["max_booking_teu"]
            )

    for priority, min_accept_teu in instance["service_requirements"].items():
        achieved = accepted_teu_by_priority[priority]
        shortfall = min_accept_teu - achieved
        if shortfall > 1e-8:
            issues.append(
                f"service floor missed for {priority}: accepted {achieved:.8f}, min {min_accept_teu:.8f}"
            )
        if min_accept_teu > 0:
            max_hard_residual = max(max_hard_residual, shortfall / min_accept_teu)

    if nominal_modal_expr < -1e-8:
        issues.append(f"nominal modal-share constraint violated by {-nominal_modal_expr:.8f}")
    total_nominal_teu_legs = sum(
        accepted_nominal[order_id].total_teu_legs for order_id in accepted_nominal
    )
    if total_nominal_teu_legs > 0:
        max_hard_residual = max(
            max_hard_residual, max(0.0, -nominal_modal_expr) / total_nominal_teu_legs
        )

    for scenario_id in instance["scenarios"]:
        expr = scenario_modal_expr[scenario_id]
        if expr < -1e-8:
            issues.append(f"modal-share constraint violated in {scenario_id} by {-expr:.8f}")
        total_teu_legs = sum(
            path.total_teu_legs
            for (order_id, sid), path in accepted_scenario.items()
            if sid == scenario_id
        )
        if total_teu_legs > 0:
            max_hard_residual = max(max_hard_residual, max(0.0, -expr) / total_teu_legs)

    activation_cost = 0.0
    shortfall_cost = 0.0
    for contract_key, contract_data in instance["contracts"].items():
        used = contract_usage[contract_key]
        if used > 1e-8:
            activation_cost += contract_data["activation_cost"]
            shortfall_cost += max(0.0, contract_data["min_booking_teu"] - used) * contract_data[
                "shortfall_cost_per_teu"
            ]

    overflow_cost = defaultdict(float)
    for resource_key, resource_data in instance["resource_rows"].items():
        overflow_cost[resource_key[0]] += max(
            0.0, resource_usage[resource_key] - resource_data["capacity_teu"]
        ) * resource_data["overflow_cost_per_teu"]

    emission_penalty = defaultdict(float)
    for scenario_id in instance["scenarios"]:
        emission_penalty[scenario_id] = (
            max(
                0.0,
                scenario_emissions[scenario_id]
                - float(instance["config"]["emission_cap_kg_per_scenario"]),
            )
            * float(instance["config"]["emission_penalty_per_kg"])
        )

    scenario_cost = {}
    for scenario_id in instance["scenarios"]:
        scenario_cost[scenario_id] = (
            scenario_pair_cost[scenario_id]
            + overflow_cost[scenario_id]
            + emission_penalty[scenario_id]
        )

    expected_scenario_cost = sum(
        instance["scenario_prob"][scenario_id] * scenario_cost[scenario_id]
        for scenario_id in instance["scenarios"]
    )
    alpha = float(instance["config"]["tail_risk_alpha"])
    sorted_costs = sorted(
        (scenario_cost[scenario_id], instance["scenario_prob"][scenario_id])
        for scenario_id in instance["scenarios"]
    )
    best_cvar = float("inf")
    candidate_etas = sorted({cost for cost, _ in sorted_costs} | {0.0})
    for eta in candidate_etas:
        cvar = eta + (1.0 / (1.0 - alpha)) * sum(
            prob * max(0.0, cost - eta) for cost, prob in sorted_costs
        )
        best_cvar = min(best_cvar, cvar)
    total_objective = (
        total_reject_cost
        + total_booking_cost
        + activation_cost
        + shortfall_cost
        + expected_scenario_cost
        + float(instance["config"]["tail_risk_weight"]) * best_cvar
    )

def solve_instance() -> dict:
    instance = load_instance(DATA_DIR)
    path_data = build_path_data(instance)

    config_limit = float(instance["config"].get("default_time_limit_seconds", 300))
    env_limit = os.getenv("ORCLAW_SOLVE_TIME_LIMIT_SECONDS")
    if env_limit is not None:
        time_limit = min(config_limit, float(env_limit))
    else:
        time_limit = config_limit

    start = time.time()
    model, vars_data = build_model(instance, path_data, time_limit)
    model.optimize()
    elapsed = time.time() - start

    result = {
        "status": str(model.getStatus()),
        "time_limit_seconds": time_limit,
        "elapsed_seconds": elapsed,
        "forced_reject_orders": sorted(path_data["forced_reject"]),
        "n_solutions": int(model.getNSols()),
        "primal_bound": None,
        "dual_bound": None,
        "gap": None,
        "solution_metrics": None,
    }
    if model.getNSols() > 0 and model.getBestSol() is not None:
        result["primal_bound"] = float(model.getObjVal())
        result["dual_bound"] = float(model.getDualbound())
        try:
            result["gap"] = float(model.getGap())
        except Exception:
            result["gap"] = None
        solution = extract_solution(instance, path_data, model, vars_data)
        write_solution(solution, SOLUTION_PATH)
        result["solution_metrics"] = compute_solution_metrics(instance, path_data, solution)
    return result
