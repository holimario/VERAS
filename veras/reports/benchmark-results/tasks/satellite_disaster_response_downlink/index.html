# Advanced MIP Patterns

## Use when

- The formulation needs logical implications, fixed charges, activation decisions, ordering, no-overlap, disjunctions, min/max, absolute values, tiers, route state, or resource calendars.
- A simple LP/MIP is producing unrealistic behavior because decisions are not linked tightly enough.
- The model is slow or infeasible and the likely cause is weak big-M logic, excessive pairwise variables, or missing state transitions.

## Do not use when

- A continuous LP is sufficient and adding binaries would not represent a real decision.
- The task is better handled by a specialized CP-SAT, constraint programming, nonlinear, or simulation method and the user did not require MIP.
- The user only needs a high-level explanation; do not introduce advanced constructs unless they clarify the actual model.

## General boundary rules

- Add binaries only for real yes/no choices, disjunctions, or nonconvex structure.
- Prefer the tightest formulation that matches the business rule; avoid decorative binaries.
- Use solver-native constructs when they improve clarity and are supported by the target environment.
- If a construct makes the model much slower, compare it with a simpler valid alternative before keeping it.

## Fixed charge and activation

- Use a binary `y` for whether an activity/resource is active.
- Link activity with a tight bound: `x <= U * y`.
- Add lower activation only when the business requires minimum use: `x >= L * y`.
- Charge fixed cost once through `fixed_cost * y`, not per unit.
- Do not force `y = 1` whenever `x = 0` unless the activity is mandatory.
- If there are startup/shutdown costs over time, separate active state from transition state.

## Logical rules

- Prefer solver-native indicator constraints for simple if-then rules when they keep the model clearer.
- If using big-M, derive M from data bounds and keep one M per rule family when possible.
- For either-or choices, use binaries whose sum is exactly one or at most one, matching the business rule.
- Distinguish implication (`A -> B`) from equivalence (`A <-> B`); the reverse direction often needs a separate constraint.
- For conditional capacity, link both activity and resource use to the condition.

## Min, max, absolute value

- For `z = max(a, b)`, add `z >= a`, `z >= b`, and objective pressure if minimizing z. Use binaries only when equality is needed without objective pressure.
- For absolute deviation `d = |x - target|`, add `d >= x - target` and `d >= target - x`.
- For service-level penalties, separate hard feasibility from soft penalty variables.
- For `min`, either transform with signs or add binaries when equality is not enforced by the objective.
- For ratio constraints, cross-multiply only when denominators are constant or safely bounded away from zero.

## Sequencing and no-overlap

- For jobs sharing a resource, use order binary `before[i,j]`.
- Typical pattern:
  - `start[j] >= end[i] - M * (1 - before[i,j])`
  - `start[i] >= end[j] - M * before[i,j]`
- Compute M from the scheduling horizon, not from an arbitrary large number.
- Include setup, cleanup, travel, rest, or turnover time in the correct side of the ordering constraint.
- Create pairwise order variables only for pairs that can share a resource or conflict.
- If time is discrete and the horizon is small, a time-indexed model may be cleaner than pairwise disjunctions.

## Piecewise and tiers

- Use solver-native piecewise-linear features for convex piecewise costs when suitable.
- For nonconvex tiers, use explicit segment variables and segment activation binaries.
- Ensure tier quantities sum to the original activity and each tier has its own upper bound.
- Distinguish incremental tiers from all-units tiers; their formulations and costs differ.
- Check whether discount tiers create nonconvex incentives that require binary selection.

## State and inventory logic

- State variables need initial conditions, transition equations, and terminal requirements if the business specifies them.
- Route or schedule state should be advanced in event order, not checked only row by row.
- Recovery, restock, cleaning, cooldown, maintenance, and rest rules often require cumulative state or last-event logic.
- If state can reset, model the reset trigger and its resource/time cost.

## Debugging advanced models

- First solve a relaxed or smaller instance and inspect whether the intended binaries activate.
- Add named constraints so IIS output points to business rules.
- If the reference solution is infeasible, replay the relevant state transitions manually before changing the evaluator.
- If the LP relaxation is very weak, inspect big-M values, missing lower/upper links, and symmetry.
- If the model is unexpectedly infeasible, test each advanced rule family on a tiny instance with a known feasible solution.

# Optimization Modeling Core

## Use when

- The user gives a word problem, business process, paper scenario, or benchmark prompt and expects a formal optimization model.
- Solver code exists but the issue appears to be a missing or incorrect formulation.
- The task asks for a complete model, not only a heuristic, simulation, or data summary.

## Do not use when

- The task is purely about software plumbing, visualization, data cleaning, or report writing.
- The problem is already fully formulated and the user only asks for code translation into a specific solver; use the solver-specific skill as the primary guide.
- The request is exploratory and the user explicitly wants brainstorming without implementation.

## Model-first workflow

1. Restate the business decision in plain language.
2. Identify sets, indices, units, and time granularity.
3. Extract parameters from data files and confirm units.
4. Define decision variables with domains and business meaning.
5. Write the objective with every cost, reward, penalty, and service term.
6. Write constraints grouped by operational rule.
7. Check edge cases: missing eligibility, impossible demand, fixed commitments, and terminal-state requirements.
8. Only then implement code.

## Ambiguity handling

- If the brief is ambiguous but data and examples imply a convention, state the assumption and continue.
- If ambiguity changes feasibility, objective direction, or deliverable schema, ask before coding or implement the least risky interpretation with a clear note.
- If units conflict across files, normalize units explicitly before modeling.
- If a hard requirement conflicts with data, diagnose the conflict before adding slack variables.

## Formulation checklist

- Every row in an input table should either become a parameter, an eligibility rule, or be explicitly irrelevant.
- Every decision variable should appear in at least one binding constraint and usually in the objective.
- Demand balance should use the correct equality or inequality direction; do not weaken equality to `>=` unless surplus is genuinely allowed.
- Capacity constraints should include activation/open/setup binaries when the business says inactive resources cannot produce, ship, or serve.
- Shortage, backlog, overtime, outsourcing, and postponement variables need explicit cost and bounds.
- Multi-period models need state transition equations and initial/terminal states.
- If the user asks for explanation, describe the modeling logic in business terms after solving.

## Constraint boundary rules

- Hard constraints represent physical impossibility, policy mandates, legal requirements, or explicit benchmark feasibility rules.
- Soft constraints need penalty variables or objective terms; do not silently turn hard constraints into penalties.
- Service levels should specify numerator, denominator, eligible population, and time window.
- Fairness constraints should define the comparison group and whether unavailable resources count.
- Logical implications need both directions only when the business rule says equivalence, not merely implication.

## Objective boundary rules

- Confirm whether the problem minimizes cost, maximizes profit, maximizes service, or uses lexicographic priorities.
- Do not mix penalties with primary economics unless their scale is intentional.
- Include fixed costs only once per activated entity.
- Include revenue only for fulfilled demand or accepted jobs, not for unmet or canceled work.
- Keep reporting metrics separate from optimized objective terms unless the prompt explicitly optimizes them.

## Implementation expectations

- Use structured parsing for CSV/JSON instead of manual string manipulation.
- Keep solver code, solution export, and validation code clearly separated.
- For benchmark or task environments, read the provided brief before coding and follow the expected output schema exactly.
- When comparing two answers, diagnose concrete formulation differences and objective consequences, not only feasibility.
- Write exported solutions at the precision expected by the checker; avoid unnecessary rounding.
- Preserve the input schema and output schema unless the user asks to redesign the benchmark.

## Verification boundary

- Verify feasibility independently from solver status when an evaluator or checker exists.
- Recompute objective from exported artifacts, not only from in-memory solver expressions.
- For benchmark tasks, create at least one negative check for each newly added rule when practical.
- For paper or real-world tasks, separate what is directly supported by the source from synthetic or assumed data.

## Red flags

- Objective terms that are counted twice or charged at the wrong marginal rate.
- Binary variables not linked tightly enough to continuous activity.
- Time periods shifted by one index.
- Average or fairness constraints that ignore the denominator or eligibility set.
- Public prompt files that reveal solver-ready variables or formulas when the benchmark is meant to test modeling translation.
- A feasible solution that exploits missing eligibility, free disposal, negative cycles, or unbounded production.
- A model that reports optimality after a time limit, infeasible status, or missing incumbent.

# Satellite Disaster-Response Downlink

A mission operations team is scheduling a short Earth-observation response
campaign after several disaster agencies submit urgent image requests. The team
must decide which requests to image before the actual cloud and downlink
disruption scenario is known. After a scenario is realized, it can adapt the
downlink plan using the observed imagery that is onboard each satellite.

You are helping an Earth-observation mission operations team plan a short
disaster-response horizon. Several agile satellites can image flood, wildfire,
storm-surge, urban-damage, river, and landslide requests, store the imagery
onboard, and downlink it through a small ground-station network. The exact cloud
and station-disruption scenario is unknown when the imaging plan is chosen, but
the downlink plan can adapt after the scenario is known.

The goal is to maximize response value after observation cost, downlink cost,
critical-request penalties, and tail-risk exposure are considered. A request is
valuable only in scenarios where its image is usable and its complete data volume
is downlinked by its deadline.

## Data

`satellites.csv` lists each satellite's onboard memory, initial memory, battery
energy, solar recharge per slot, downlink energy use, downlink thermal load,
and rolling thermal limit.

`ground_stations.csv` lists the available stations and how many simultaneous
satellite contacts each station can support in one slot.

`requests.csv` lists the disaster image requests, criticality, data size, value,
deadline, region, and any stereo-pair grouping. A stereo-pair bonus is earned in
a scenario only when every request in that pair is delivered in that scenario.

`observation_windows.csv` lists the satellite/slot choices that can image each
request, including instrument type, image energy, slew class, and thermal load.

`downlink_windows.csv` lists satellite-to-ground-station contacts and their
nominal data capacity.

`scenarios.csv` gives the probability and target profit for each disruption
scenario.

`scenario_observation_quality.csv` says whether each request is usable in each
scenario and how its delivered value changes.

`scenario_downlink_multipliers.csv` gives the scenario-specific capacity
multiplier for each ground station and slot. A zero multiplier means that contact
capacity is unavailable in that scenario.

`region_ingest_capacity.csv` gives the maximum GB that each disaster-region
analysis cell can ingest in each scenario and slot. It represents analyst,
network, and emergency-command processing limits after the data reaches the
ground.

`config.json` contains planning constants, service floors, costs, and the
tail-risk settings.

## Operating Rules

Observation decisions are first-stage decisions. They must not depend on the
scenario. Downlink decisions are scenario-specific recourse decisions.

Each request can be observed at most once, and only through a listed observation
window. A satellite can perform at most one observation in a slot. If either of
two consecutive observations for the same satellite is marked as high-slew,
there must be a recovery slot between them.

Each satellite has a maximum number of observations over the horizon. It cannot
observe and downlink in the same slot in any scenario. It also has a rolling
thermal envelope. For every scenario, the sum of observation thermal loads and
downlink thermal loads over each configured rolling slot window must stay within
that satellite's thermal limit.

Downlink rows must use listed contacts. In each scenario, the contact capacity is
the nominal contact capacity multiplied by that scenario's station-slot
multiplier. Ground-station antenna counts limit the number of satellites using a
station in the same slot. Data for a request can only be downlinked by the
satellite that observed it, and only after the observation slot. Full request
data must be downlinked by the request deadline to receive credit.

Downlinked data also consumes disaster-region ingest capacity. In a given
scenario and slot, all downlinked GB for requests from the same disaster region
must fit inside that region's ingest capacity for the slot.

For every scenario and satellite, onboard memory and battery energy are tracked
through time. Observations add data to memory and consume image energy.
Downlinks remove data from memory and consume energy per GB. Solar recharge is
available each slot up to the satellite's battery capacity. Battery energy must
stay above the reserve level, and memory must stay within capacity and
nonnegative.

In each scenario, the delivered plan must satisfy the configured critical-request
delivery floor, regional coverage floor, and delivered-value floor over usable
requests.

The score is based on expected scenario profit minus first-stage observation
cost and a weighted tail-risk loss. Scenario profit includes delivered image
value, stereo-pair bonuses, downlink cost, and penalties for usable critical
requests that were not delivered.

- `satellite_id`, `slot`, and `ground_station` identify a listed contact;
- `request_id` identifies the image data being transmitted;
- `mode` is `downlink`;
- `quantity` is the GB transmitted on that row.

# Satellite Disaster-Response Downlink Model

## Modeling choice

This instance is best represented as a two-stage stochastic mixed-integer program in extensive form.

- First stage: choose a nonanticipative observation plan, meaning which observation window to use for each request before the disruption scenario is known.
- Second stage: for each public scenario, choose a scenario-specific downlink plan for the observed images.

An extensive-form MIP is appropriate here because the public instance is moderate in size: 48 requests, 144 observation windows, 66 downlink contacts, and 4 scenarios. That size is small enough to model all scenarios directly while keeping the stronger nonanticipativity, memory, energy, thermal, and service-floor constraints in one model.

## Sets and indices

- `S`: scenarios.
- `K`: satellites.
- `T = {1, ..., H}`: planning slots, where `H = 24`.
- `G`: ground stations.
- `R`: requests.
- `W`: listed observation windows.
- `C`: listed downlink contacts.
- `P`: stereo pairs with nonblank `stereo_pair_id`.
- `U`: disaster regions.

Useful subsets:

- `W_r`: observation windows for request `r`.
- `W_{k,t}`: observation windows for satellite `k` in slot `t`.
- `W^H_{k,t}`: high-slew observation windows for satellite `k` in slot `t`.
- `C_{k,t}`: downlink contacts for satellite `k` in slot `t`.
- `C_{g,t}`: downlink contacts using ground station `g` in slot `t`.
- `R_u`: requests from region `u`.
- `R_p`: requests in stereo pair `p`.

For each request-contact combination, a downlink variable is created only when the contact belongs to a satellite that could observe that request and the contact slot is strictly after at least one feasible observation slot and no later than the request deadline.

## Parameters

From the public data:

- `prob_s`: scenario probability.
- `target_s`: scenario target profit used in the tail-risk term.
- `size_r`: request data volume in GB.
- `value_r`: base mission value.
- `deadline_r`: deadline slot.
- `crit_r in {0,1}`: whether request `r` is critical.
- `usable_{s,r} in {0,1}`: whether request `r` is usable in scenario `s`.
- `mult_{s,r}`: scenario value multiplier.
- `cap_c`: nominal contact capacity in GB.
- `multdl_{s,g,t}`: scenario-specific station-slot capacity multiplier.
- `ingest_{s,u,t}`: region ingest capacity in GB.
- `obsEnergy_w`, `obsTherm_w`, `sat_w`, `req_w`, `slot_w`, `slew_w`: observation-window data.
- `memCap_k`, `mem0_k`, `energyCap_k`, `energy0_k`, `solar_k`, `dlEnergy_k`, `dlTherm_k`, `thermLim_k`: satellite data.
- `ant_g`: number of antennas at station `g`.
- `obsCost`, `dlCost`, `critPenalty`, `stereoBonus`, `alpha`, `tailWeight`, `minCritFrac`, `minValueFrac`, `minRegions`, `maxObsPerSat`, `reserveEnergy`, `rollWindow`: constants from `config.json`.

Derived values:

- Scenario delivered value coefficient:
  - `val_{s,r} = value_r * mult_{s,r}`.
- Scenario contact capacity:
  - `scCap_{s,c} = cap_c * multdl_{s,station(c),slot(c)}`.
- Usable critical count:
  - `UC_s = sum_{r in R} crit_r * usable_{s,r}`.
- Total usable delivered-value denominator:
  - `UV_s = sum_{r in R} val_{s,r} * usable_{s,r}`.

## Decision variables

First-stage variables:

- `x_w in {0,1}`: 1 if observation window `w` is selected.

Second-stage scenario variables:

- `y_{s,c,r} >= 0`: GB of request `r` downlinked on contact `c` in scenario `s`.
- `z_{s,c} in {0,1}`: 1 if contact `c` is used in scenario `s`.
- `d_{s,r} in {0,1}`: 1 if request `r` is fully delivered by its deadline in scenario `s`.
- `b_{s,p} in {0,1}`: 1 if every request in stereo pair `p` is delivered in scenario `s`.
- `q_{s,u} in {0,1}`: 1 if region `u` receives at least one delivered request in scenario `s`.
- `mem_{s,k,t} >= 0`: onboard memory after slot `t`.
- `energy_{s,k,t} >= 0`: battery energy after slot `t`.
- `recharge_{s,k,t} >= 0`: chosen solar recharge in slot `t`, bounded by the public per-slot recharge limit.

Risk variables:

- `loss_s >= 0`: shortfall of scenario profit below the public target.
- `eta` free: VaR-like threshold for CVaR.
- `excess_s >= 0`: excess loss above `eta`.

## Objective

Let scenario operating profit be

`profit_s = sum_r val_{s,r} d_{s,r}
          + sum_p stereoBonus b_{s,p}
          - sum_{c,r} dlCost y_{s,c,r}
          - sum_r critPenalty * crit_r * usable_{s,r} * (1 - d_{s,r})`.

The first-stage observation cost is

`ObsCost = obsCost * sum_w x_w`.

The public tail-risk term is modeled as CVaR of target shortfall:

- `loss_s >= target_s - profit_s`
- `loss_s >= 0`
- `excess_s >= loss_s - eta`
- `excess_s >= 0`
- `CVaR = eta + (1 / (1 - alpha)) * sum_s prob_s * excess_s`

The objective is

`maximize sum_s prob_s * profit_s - ObsCost - tailWeight * CVaR`.

This follows the public statement: maximize expected scenario profit, subtract first-stage observation cost, and subtract a weighted tail-risk loss.

## Constraints

### 1. Observation selection and nonanticipativity

- Each request is observed at most once:
  - `sum_{w in W_r} x_w <= 1` for all `r`.
- Each satellite performs at most one observation per slot:
  - `sum_{w in W_{k,t}} x_w <= 1` for all `k,t`.
- Each satellite respects the horizon observation count limit:
  - `sum_{w: sat_w = k} x_w <= maxObsPerSat` for all `k`.

Because `x` is common to all scenarios, first-stage nonanticipativity is enforced directly.

### 2. High-slew recovery

Let

- `obs_{k,t} = sum_{w in W_{k,t}} x_w`
- `high_{k,t} = sum_{w in W^H_{k,t}} x_w`

Then consecutive observations are forbidden when either one is high-slew:

- `high_{k,t} + obs_{k,t+1} <= 1` for all `k, t = 1,...,H-1`
- `obs_{k,t} + high_{k,t+1} <= 1` for all `k, t = 1,...,H-1`

This exactly matches the public rule.

### 3. Contact usage and station limits

For every scenario and contact:

- Link downlink quantity to contact activation:
  - `sum_r y_{s,c,r} <= scCap_{s,c} z_{s,c}`.
- Ground-station antenna limit:
  - `sum_{c in C_{g,t}} z_{s,c} <= ant_g` for all `s,g,t`.
- A satellite cannot observe and downlink in the same slot:
  - `sum_{w in W_{k,t}} x_w + sum_{c in C_{k,t}} z_{s,c} <= 1` for all `s,k,t`.

### 4. Downlink-request feasibility

Only the observing satellite may downlink a request, and only after observation.

For every created variable `y_{s,c,r}`, let `A(c,r)` be the set of observation windows for request `r` on the same satellite as contact `c` with `slot_w < slot_c`. Then:

- `y_{s,c,r} <= size_r * sum_{w in A(c,r)} x_w`.

This simultaneously enforces satellite assignment and temporal precedence.

Each delivered request must have its complete volume downlinked by its deadline:

- `sum_c y_{s,c,r} = size_r * d_{s,r}` for all `s,r`.
- `d_{s,r} <= usable_{s,r}` for all `s,r`.

Because variables `y_{s,c,r}` are created only on contacts with `slot_c <= deadline_r`, the equality forces full on-time delivery whenever `d_{s,r} = 1`.

### 5. Region ingest limits

For every scenario, region, and slot:

- `sum_{c: slot_c=t} sum_{r in R_u} y_{s,c,r} <= ingest_{s,u,t}`.

### 6. Memory dynamics

For each scenario and satellite, memory evolves by slot:

- `mem_{s,k,0} = mem0_k`.
- `mem_{s,k,t} = mem_{s,k,t-1}
               + sum_{w in W_{k,t}} size_{req_w} x_w
               - sum_{c in C_{k,t}} sum_r y_{s,c,r}`.
- `0 <= mem_{s,k,t} <= memCap_k`.

Initial memory is treated as occupied carry-in storage that reduces available capacity throughout the horizon unless new request data is downlinked away.

### 7. Energy dynamics

For each scenario and satellite:

- `energy_{s,k,0} = energy0_k`.
- `energy_{s,k,t} = energy_{s,k,t-1}
                  - sum_{w in W_{k,t}} obsEnergy_w x_w
                  - dlEnergy_k * sum_{c in C_{k,t}} sum_r y_{s,c,r}
                  + recharge_{s,k,t}`.
- `0 <= recharge_{s,k,t} <= solar_k`.
- `reserveEnergy <= energy_{s,k,t} <= energyCap_k`.

This models solar recharge as a controllable amount up to the public per-slot recharge limit and battery capacity.

### 8. Rolling thermal envelope

For each scenario, satellite, and slot `t`, over the public rolling window length `rollWindow`:

`sum_{tau=max(1,t-rollWindow+1)}^t
  [sum_{w in W_{k,tau}} obsTherm_w x_w
   + dlTherm_k * sum_{c in C_{k,tau}} sum_r y_{s,c,r}]
 <= thermLim_k`

### 9. Scenario service floors

Critical-delivery floor:

- `sum_r crit_r * usable_{s,r} * d_{s,r} >= minCritFrac * UC_s` for all `s` with `UC_s > 0`.

Delivered-value floor over usable requests:

- `sum_r val_{s,r} d_{s,r} >= minValueFrac * UV_s` for all `s`.

Regional coverage floor:

- `sum_{r in R_u} d_{s,r} >= q_{s,u}` for all `s,u`.
- `sum_u q_{s,u} >= minRegions` for all `s`.

### 10. Stereo-pair bonuses

For each scenario and stereo pair:

- `b_{s,p} <= d_{s,r}` for all `r in R_p`.
- `b_{s,p} >= sum_{r in R_p} d_{s,r} - |R_p| + 1`.

This makes `b_{s,p} = 1` exactly when every request in the pair is delivered in that scenario.

## Public-data assumptions

Two public fields are not operationally defined by the problem statement:

- `quality_score` in `observation_windows.csv`
- `late_penalty_per_slot` in `config.json`

The public rules never state that value depends on `quality_score`, and they state that a request receives credit only if its full data volume is downlinked by its deadline. Therefore the implemented optimization uses the literal public scoring rules:

- delivered request value depends on `mission_value` and the scenario multiplier only;
- no value is granted for incomplete or late delivery;
- no extra late-delivery penalty term is applied because the public statement does not define a valid late-delivery reward/penalty mechanism.

These assumptions are documented explicitly so the solver remains faithful to the public benchmark text instead of inventing unannounced economics.

## Why this formulation is strong

- First-stage nonanticipativity is exact because observations are represented only once.
- Full-delivery binaries `d_{s,r}` avoid weak partial-credit behavior.
- Contact-use binaries `z_{s,c}` make antenna and observe/downlink exclusion constraints tight.
- Memory, energy, ingest, and rolling thermal constraints are modeled directly in slot time, which is compact here because the horizon has only 24 slots.
- Sparse downlink variables are created only for satellite-request-contact combinations that are temporally and physically possible.

# Optimization Modeling Core

## Use when

- The user gives a word problem, business process, paper scenario, or benchmark prompt and expects a formal optimization model.
- Solver code exists but the issue appears to be a missing or incorrect formulation.
- The task asks for a complete model, not only a heuristic, simulation, or data summary.

## Do not use when

- The task is purely about software plumbing, visualization, data cleaning, or report writing.
- The problem is already fully formulated and the user only asks for code translation into a specific solver; use the solver-specific skill as the primary guide.
- The request is exploratory and the user explicitly wants brainstorming without implementation.

## Model-first workflow

1. Restate the business decision in plain language.
2. Identify sets, indices, units, and time granularity.
3. Extract parameters from data files and confirm units.
4. Define decision variables with domains and business meaning.
5. Write the objective with every cost, reward, penalty, and service term.
6. Write constraints grouped by operational rule.
7. Check edge cases: missing eligibility, impossible demand, fixed commitments, and terminal-state requirements.
8. Only then implement code.

## Ambiguity handling

- If the brief is ambiguous but data and examples imply a convention, state the assumption and continue.
- If ambiguity changes feasibility, objective direction, or deliverable schema, ask before coding or implement the least risky interpretation with a clear note.
- If units conflict across files, normalize units explicitly before modeling.
- If a hard requirement conflicts with data, diagnose the conflict before adding slack variables.

## Formulation checklist

- Every row in an input table should either become a parameter, an eligibility rule, or be explicitly irrelevant.
- Every decision variable should appear in at least one binding constraint and usually in the objective.
- Demand balance should use the correct equality or inequality direction; do not weaken equality to `>=` unless surplus is genuinely allowed.
- Capacity constraints should include activation/open/setup binaries when the business says inactive resources cannot produce, ship, or serve.
- Shortage, backlog, overtime, outsourcing, and postponement variables need explicit cost and bounds.
- Multi-period models need state transition equations and initial/terminal states.
- If the user asks for explanation, describe the modeling logic in business terms after solving.

## Constraint boundary rules

- Hard constraints represent physical impossibility, policy mandates, legal requirements, or explicit benchmark feasibility rules.
- Soft constraints need penalty variables or objective terms; do not silently turn hard constraints into penalties.
- Service levels should specify numerator, denominator, eligible population, and time window.
- Fairness constraints should define the comparison group and whether unavailable resources count.
- Logical implications need both directions only when the business rule says equivalence, not merely implication.

## Objective boundary rules

- Confirm whether the problem minimizes cost, maximizes profit, maximizes service, or uses lexicographic priorities.
- Do not mix penalties with primary economics unless their scale is intentional.
- Include fixed costs only once per activated entity.
- Include revenue only for fulfilled demand or accepted jobs, not for unmet or canceled work.
- Keep reporting metrics separate from optimized objective terms unless the prompt explicitly optimizes them.

## Implementation expectations

- Use structured parsing for CSV/JSON instead of manual string manipulation.
- Keep solver code, solution export, and validation code clearly separated.
- For benchmark or task environments, read the provided brief before coding and follow the expected output schema exactly.
- When comparing two answers, diagnose concrete formulation differences and objective consequences, not only feasibility.
- Write exported solutions at the precision expected by the checker; avoid unnecessary rounding.

- Verify feasibility independently from solver status when an evaluator or checker exists.
- Recompute objective from exported artifacts, not only from in-memory solver expressions.
- For benchmark tasks, create at least one negative check for each newly added rule when practical.
- For paper or real-world tasks, separate what is directly supported by the source from synthetic or assumed data.

- Objective terms that are counted twice or charged at the wrong marginal rate.

- Time periods shifted by one index.

- A feasible solution that exploits missing eligibility, free disposal, negative cycles, or unbounded production.

window. A satellite can perform at most one observation in a slot. If either of
two consecutive observations for the same satellite is marked as high-slew,
there must be a recovery slot between them.

Each satellite has a maximum number of observations over the horizon. It cannot
observe and downlink in the same slot in any scenario. It also has a rolling
thermal envelope. For every scenario, the sum of observation thermal loads and
downlink thermal loads over each configured rolling slot window must stay within
that satellite's thermal limit.

Downlink rows must use listed contacts. In each scenario, the contact capacity is
the nominal contact capacity multiplied by that scenario's station-slot
multiplier. Ground-station antenna counts limit the number of satellites using a
station in the same slot. Data for a request can only be downlinked by the
satellite that observed it, and only after the observation slot. Full request
data must be downlinked by the request deadline to receive credit.

Downlinked data also consumes disaster-region ingest capacity. In a given
scenario and slot, all downlinked GB for requests from the same disaster region
must fit inside that region's ingest capacity for the slot.

For every scenario and satellite, onboard memory and battery energy are tracked
through time. Observations add data to memory and consume image energy.
Downlinks remove data from memory and consume energy per GB. Solar recharge is
available each slot up to the satellite's battery capacity. Battery energy must
stay above the reserve level, and memory must stay within capacity and
nonnegative.

In each scenario, the delivered plan must satisfy the configured critical-request
delivery floor, regional coverage floor, and delivered-value floor over usable
requests.

The score is based on expected scenario profit minus first-stage observation
cost and a weighted tail-risk loss. Scenario profit includes delivered image
value, stereo-pair bonuses, downlink cost, and penalties for usable critical
requests that were not delivered.

# Advanced MIP Patterns

## Use when

- The formulation needs logical implications, fixed charges, activation decisions, ordering, no-overlap, disjunctions, min/max, absolute values, tiers, route state, or resource calendars.
- A simple LP/MIP is producing unrealistic behavior because decisions are not linked tightly enough.
- The model is slow or infeasible and the likely cause is weak big-M logic, excessive pairwise variables, or missing state transitions.

## Do not use when

- A continuous LP is sufficient and adding binaries would not represent a real decision.
- The task is better handled by a specialized CP-SAT, constraint programming, nonlinear, or simulation method and the user did not require MIP.
- The user only needs a high-level explanation; do not introduce advanced constructs unless they clarify the actual model.

## General boundary rules

- Add binaries only for real yes/no choices, disjunctions, or nonconvex structure.
- Prefer the tightest formulation that matches the business rule; avoid decorative binaries.
- Use solver-native constructs when they improve clarity and are supported by the target environment.
- If a construct makes the model much slower, compare it with a simpler valid alternative before keeping it.

## Fixed charge and activation

- Use a binary `y` for whether an activity/resource is active.
- Link activity with a tight bound: `x <= U * y`.
- Add lower activation only when the business requires minimum use: `x >= L * y`.
- Charge fixed cost once through `fixed_cost * y`, not per unit.
- Do not force `y = 1` whenever `x = 0` unless the activity is mandatory.
- If there are startup/shutdown costs over time, separate active state from transition state.

## Logical rules

- Prefer solver-native indicator constraints for simple if-then rules when they keep the model clearer.
- If using big-M, derive M from data bounds and keep one M per rule family when possible.
- For either-or choices, use binaries whose sum is exactly one or at most one, matching the business rule.
- Distinguish implication (`A -> B`) from equivalence (`A <-> B`); the reverse direction often needs a separate constraint.
- For conditional capacity, link both activity and resource use to the condition.

## Min, max, absolute value

- For `z = max(a, b)`, add `z >= a`, `z >= b`, and objective pressure if minimizing z. Use binaries only when equality is needed without objective pressure.
- For absolute deviation `d = |x - target|`, add `d >= x - target` and `d >= target - x`.
- For service-level penalties, separate hard feasibility from soft penalty variables.
- For `min`, either transform with signs or add binaries when equality is not enforced by the objective.
- For ratio constraints, cross-multiply only when denominators are constant or safely bounded away from zero.

## Sequencing and no-overlap

- For jobs sharing a resource, use order binary `before[i,j]`.
- Typical pattern:
  - `start[j] >= end[i] - M * (1 - before[i,j])`
  - `start[i] >= end[j] - M * before[i,j]`
- Compute M from the scheduling horizon, not from an arbitrary large number.
- Include setup, cleanup, travel, rest, or turnover time in the correct side of the ordering constraint.
- Create pairwise order variables only for pairs that can share a resource or conflict.
- If time is discrete and the horizon is small, a time-indexed model may be cleaner than pairwise disjunctions.

## Piecewise and tiers

- Use solver-native piecewise-linear features for convex piecewise costs when suitable.
- For nonconvex tiers, use explicit segment variables and segment activation binaries.
- Ensure tier quantities sum to the original activity and each tier has its own upper bound.
- Distinguish incremental tiers from all-units tiers; their formulations and costs differ.
- Check whether discount tiers create nonconvex incentives that require binary selection.

## State and inventory logic

- State variables need initial conditions, transition equations, and terminal requirements if the business specifies them.
- Route or schedule state should be advanced in event order, not checked only row by row.
- Recovery, restock, cleaning, cooldown, maintenance, and rest rules often require cumulative state or last-event logic.
- If state can reset, model the reset trigger and its resource/time cost.

## Debugging advanced models

- First solve a relaxed or smaller instance and inspect whether the intended binaries activate.
- Add named constraints so IIS output points to business rules.
- If the reference solution is infeasible, replay the relevant state transitions manually before changing the evaluator.
- If the LP relaxation is very weak, inspect big-M values, missing lower/upper links, and symmetry.
- If the model is unexpectedly infeasible, test each advanced rule family on a tiny instance with a known feasible solution.

# Advanced MIP Patterns

## Use when

- The formulation needs logical implications, fixed charges, activation decisions, ordering, no-overlap, disjunctions, min/max, absolute values, tiers, route state, or resource calendars.
- A simple LP/MIP is producing unrealistic behavior because decisions are not linked tightly enough.
- The model is slow or infeasible and the likely cause is weak big-M logic, excessive pairwise variables, or missing state transitions.

## Do not use when

- A continuous LP is sufficient and adding binaries would not represent a real decision.
- The task is better handled by a specialized CP-SAT, constraint programming, nonlinear, or simulation method and the user did not require MIP.
- The user only needs a high-level explanation; do not introduce advanced constructs unless they clarify the actual model.

## General boundary rules

- Add binaries only for real yes/no choices, disjunctions, or nonconvex structure.
- Prefer the tightest formulation that matches the business rule; avoid decorative binaries.
- Use solver-native constructs when they improve clarity and are supported by the target environment.
- If a construct makes the model much slower, compare it with a simpler valid alternative before keeping it.

## Fixed charge and activation

- Use a binary `y` for whether an activity/resource is active.
- Link activity with a tight bound: `x <= U * y`.
- Add lower activation only when the business requires minimum use: `x >= L * y`.
- Charge fixed cost once through `fixed_cost * y`, not per unit.
- Do not force `y = 1` whenever `x = 0` unless the activity is mandatory.
- If there are startup/shutdown costs over time, separate active state from transition state.

## Logical rules

- Prefer solver-native indicator constraints for simple if-then rules when they keep the model clearer.
- If using big-M, derive M from data bounds and keep one M per rule family when possible.
- For either-or choices, use binaries whose sum is exactly one or at most one, matching the business rule.
- Distinguish implication (`A -> B`) from equivalence (`A <-> B`); the reverse direction often needs a separate constraint.
- For conditional capacity, link both activity and resource use to the condition.

## Min, max, absolute value

- For `z = max(a, b)`, add `z >= a`, `z >= b`, and objective pressure if minimizing z. Use binaries only when equality is needed without objective pressure.
- For absolute deviation `d = |x - target|`, add `d >= x - target` and `d >= target - x`.
- For service-level penalties, separate hard feasibility from soft penalty variables.
- For `min`, either transform with signs or add binaries when equality is not enforced by the objective.
- For ratio constraints, cross-multiply only when denominators are constant or safely bounded away from zero.

## Sequencing and no-overlap

- For jobs sharing a resource, use order binary `before[i,j]`.
- Typical pattern:
  - `start[j] >= end[i] - M * (1 - before[i,j])`
  - `start[i] >= end[j] - M * before[i,j]`
- Compute M from the scheduling horizon, not from an arbitrary large number.
- Include setup, cleanup, travel, rest, or turnover time in the correct side of the ordering constraint.
- Create pairwise order variables only for pairs that can share a resource or conflict.
- If time is discrete and the horizon is small, a time-indexed model may be cleaner than pairwise disjunctions.

## Piecewise and tiers

- Use solver-native piecewise-linear features for convex piecewise costs when suitable.
- For nonconvex tiers, use explicit segment variables and segment activation binaries.
- Ensure tier quantities sum to the original activity and each tier has its own upper bound.
- Distinguish incremental tiers from all-units tiers; their formulations and costs differ.
- Check whether discount tiers create nonconvex incentives that require binary selection.

## State and inventory logic

- State variables need initial conditions, transition equations, and terminal requirements if the business specifies them.
- Route or schedule state should be advanced in event order, not checked only row by row.
- Recovery, restock, cleaning, cooldown, maintenance, and rest rules often require cumulative state or last-event logic.
- If state can reset, model the reset trigger and its resource/time cost.

## Debugging advanced models

- First solve a relaxed or smaller instance and inspect whether the intended binaries activate.
- Add named constraints so IIS output points to business rules.
- If the reference solution is infeasible, replay the relevant state transitions manually before changing the evaluator.
- If the LP relaxation is very weak, inspect big-M values, missing lower/upper links, and symmetry.
- If the model is unexpectedly infeasible, test each advanced rule family on a tiny instance with a known feasible solution.

def build_model(data, time_limit):
    config = data["config"]
    satellites = data["satellites"]
    requests = data["requests"]
    observation_windows = data["observation_windows"]
    contacts = data["contacts"]
    scenarios = data["scenarios"]
    regions = data["regions"]
    stereo_pairs = data["stereo_pairs"]
    horizon_slots = data["horizon_slots"]
    usable_critical_count = data["usable_critical_count"]
    usable_total_value = data["usable_total_value"]

    model = Model("satellite_disaster_response")
    model.hideOutput()
    model.setParam("limits/gap", SCIP_GAP)
    model.setParam("limits/time", time_limit)
    model.setParam("display/verblevel", 0)

    x = {w: model.addVar(vtype="B", name=f"x[{w}]") for w in observation_windows}

    d = {}
    mem = {}
    energy = {}
    recharge = {}
    z = {}
    y = {}
    q = {}
    b = {}
    loss = {}
    excess = {}

    for scenario_id in data["scenario_order"]:
        for request_id in requests:
            ub = 1 if data["scenario_usable"][scenario_id][request_id] == 1 else 0
            d[(scenario_id, request_id)] = model.addVar(vtype="B", lb=0, ub=ub, name=f"d[{scenario_id},{request_id}]")
        for contact_id in contacts:
            cap = data["scenario_contact_capacity"][(scenario_id, contact_id)]
            ub = 1 if cap > config["quantity_tolerance"] else 0
            z[(scenario_id, contact_id)] = model.addVar(vtype="B", lb=0, ub=ub, name=f"z[{scenario_id},{contact_id}]")
        for region in regions:
            q[(scenario_id, region)] = model.addVar(vtype="B", name=f"q[{scenario_id},{region}]")
        for pair_id in stereo_pairs:
            b[(scenario_id, pair_id)] = model.addVar(vtype="B", name=f"b[{scenario_id},{pair_id}]")
        for satellite_id, sat in satellites.items():
            for slot in horizon_slots:
                mem[(scenario_id, satellite_id, slot)] = model.addVar(
                    lb=0.0, ub=sat["memory_capacity_gb"], name=f"mem[{scenario_id},{satellite_id},{slot}]"
                )
                energy[(scenario_id, satellite_id, slot)] = model.addVar(
                    lb=config["reserve_energy_kwh"], ub=sat["energy_capacity_kwh"],
                    name=f"energy[{scenario_id},{satellite_id},{slot}]"
                )
                recharge[(scenario_id, satellite_id, slot)] = model.addVar(
                    lb=0.0, ub=sat["solar_recharge_kwh_per_slot"], name=f"recharge[{scenario_id},{satellite_id},{slot}]"
                )
        loss[scenario_id] = model.addVar(lb=0.0, name=f"loss[{scenario_id}]")
        excess[scenario_id] = model.addVar(lb=0.0, name=f"excess[{scenario_id}]")

    eta = model.addVar(lb=-model.infinity(), name="eta")

    for key in data["feasible_downlink_keys"]:
        scenario_id, contact_id, request_id = key
        y[key] = model.addVar(lb=0.0, ub=requests[request_id]["data_gb"], name=f"y[{scenario_id},{contact_id},{request_id}]")

    for request_id, windows in data["obs_by_request"].items():
        model.addCons(quicksum(x[w] for w in windows) <= 1, name=f"observe_once[{request_id}]")

    for satellite_id in satellites:
        model.addCons(
            quicksum(x[w] for w, obs in observation_windows.items() if obs["satellite_id"] == satellite_id)
            <= config["max_observations_per_satellite"],
            name=f"max_obs[{satellite_id}]",
        )
        for slot in horizon_slots:
            slot_windows = data["obs_by_sat_slot"].get((satellite_id, slot), [])
            if slot_windows:
                model.addCons(quicksum(x[w] for w in slot_windows) <= 1, name=f"one_obs[{satellite_id},{slot}]")

    for satellite_id in satellites:
        for slot in horizon_slots[:-1]:
            high_now = data["obs_high_by_sat_slot"].get((satellite_id, slot), [])
            high_next = data["obs_high_by_sat_slot"].get((satellite_id, slot + 1), [])
            obs_now = data["obs_by_sat_slot"].get((satellite_id, slot), [])
            obs_next = data["obs_by_sat_slot"].get((satellite_id, slot + 1), [])
            if high_now and obs_next:
                model.addCons(
                    quicksum(x[w] for w in high_now) + quicksum(x[w] for w in obs_next) <= 1,
                    name=f"high_recovery_a[{satellite_id},{slot}]",
                )
            if obs_now and high_next:
                model.addCons(
                    quicksum(x[w] for w in obs_now) + quicksum(x[w] for w in high_next) <= 1,

                )

    for scenario_id in data["scenario_order"]:
        for contact_id in contacts:

            cap = data["scenario_contact_capacity"][(scenario_id, contact_id)]
            if y_keys:
                model.addCons(
                    quicksum(y[key] for key in y_keys) <= cap * z[(scenario_id, contact_id)],
                    name=f"contact_cap[{scenario_id},{contact_id}]",
                )
            else:
                model.addCons(z[(scenario_id, contact_id)] == 0, name=f"unused_contact[{scenario_id},{contact_id}]")

        for ground_station, station in data["ground_stations"].items():
            for slot in horizon_slots:
                contact_ids = data["contacts_by_station_slot"].get((ground_station, slot), [])
                if not contact_ids:
                    continue
                model.addCons(
                    quicksum(z[(scenario_id, contact_id)] for contact_id in contact_ids) <= station["antenna_count"],
                    name=f"antenna[{scenario_id},{ground_station},{slot}]",
                )

        for satellite_id in satellites:
            for slot in horizon_slots:
                slot_windows = data["obs_by_sat_slot"].get((satellite_id, slot), [])
                slot_contacts = data["contacts_by_sat_slot"].get((satellite_id, slot), [])
                if not slot_windows and not slot_contacts:
                    continue
                model.addCons(
                    quicksum(x[w] for w in slot_windows) + quicksum(z[(scenario_id, contact_id)] for contact_id in slot_contacts) <= 1,
                    name=f"obs_downlink_mutex[{scenario_id},{satellite_id},{slot}]",
                )

    for key, compatible_windows in data["y_compatible_windows"].items():
        scenario_id, contact_id, request_id = key
        model.addCons(
            y[key] <= requests[request_id]["data_gb"] * quicksum(x[window_id] for window_id in compatible_windows),
            name=f"downlink_obs_link[{scenario_id},{contact_id},{request_id}]",

    for scenario_id in data["scenario_order"]:
        for request_id, request in requests.items():
            y_keys = data["y_keys_by_scenario_request"].get((scenario_id, request_id), [])
            lhs = quicksum(y[key] for key in y_keys) if y_keys else 0.0
            model.addCons(lhs == request["data_gb"] * d[(scenario_id, request_id)], name=f"deliver_full[{scenario_id},{request_id}]")

    for scenario_id in data["scenario_order"]:
        for region in regions:
            for slot in horizon_slots:
                y_keys = data["y_keys_by_scenario_region_slot"].get((scenario_id, region, slot), [])
                if not y_keys:
                    continue
                model.addCons(
                    quicksum(y[key] for key in y_keys) <= data["region_ingest"][(scenario_id, region, slot)],
                    name=f"ingest[{scenario_id},{region},{slot}]",
                )

    for scenario_id in data["scenario_order"]:
        for satellite_id, sat in satellites.items():
            for slot in horizon_slots:
                obs_add = quicksum(
                    requests[observation_windows[window_id]["request_id"]]["data_gb"] * x[window_id]
                    for window_id in data["obs_by_sat_slot"].get((satellite_id, slot), [])
                )
                dl_remove_keys = data["y_keys_by_scenario_sat_slot"].get((scenario_id, satellite_id, slot), [])
                dl_remove = quicksum(y[key] for key in dl_remove_keys) if dl_remove_keys else 0.0
                previous_mem = sat["initial_memory_gb"] if slot == 1 else mem[(scenario_id, satellite_id, slot - 1)]
                model.addCons(
                    mem[(scenario_id, satellite_id, slot)] == previous_mem + obs_add - dl_remove,
                    name=f"memory[{scenario_id},{satellite_id},{slot}]",
                )

                obs_energy = quicksum(
                    observation_windows[window_id]["energy_kwh"] * x[window_id]
                    for window_id in data["obs_by_sat_slot"].get((satellite_id, slot), [])
                )
                dl_energy = sat["downlink_energy_kwh_per_gb"] * (
                    quicksum(y[key] for key in dl_remove_keys) if dl_remove_keys else 0.0
                )
                previous_energy = sat["initial_energy_kwh"] if slot == 1 else energy[(scenario_id, satellite_id, slot - 1)]
                model.addCons(
                    energy[(scenario_id, satellite_id, slot)] == previous_energy - obs_energy - dl_energy + recharge[(scenario_id, satellite_id, slot)],
                    name=f"energy_bal[{scenario_id},{satellite_id},{slot}]",
                )

            for slot in horizon_slots:
                thermal_slots = range(max(1, slot - data["rolling_window"] + 1), slot + 1)
                thermal_terms = []
                for tau in thermal_slots:
                    thermal_terms.extend(
                        observation_windows[window_id]["thermal_load"] * x[window_id]

                    tau_keys = data["y_keys_by_scenario_sat_slot"].get((scenario_id, satellite_id, tau), [])

                    quicksum(thermal_terms) <= sat["thermal_limit_rolling"],
                    name=f"thermal[{scenario_id},{satellite_id},{slot}]",

        usable_critical = usable_critical_count[scenario_id]
        if usable_critical > 0:

                quicksum(
                    requests[request_id]["critical"] * d[(scenario_id, request_id)]
                    for request_id in requests
                    if data["scenario_usable"][scenario_id][request_id] == 1

                >= config["minimum_critical_delivery_fraction"] * usable_critical,
                name=f"critical_floor[{scenario_id}]",

            quicksum(data["scenario_value"][scenario_id][request_id] * d[(scenario_id, request_id)] for request_id in requests)

            quicksum(q[(scenario_id, region)] for region in regions) >= config["minimum_regions_delivered_per_scenario"],
            name=f"region_floor[{scenario_id}]",
        )

        for pair_id, pair_requests in stereo_pairs.items():
            for request_id in pair_requests:
                model.addCons(b[(scenario_id, pair_id)] <= d[(scenario_id, request_id)], name=f"pair_ub[{scenario_id},{pair_id},{request_id}]")

                b[(scenario_id, pair_id)] >= quicksum(d[(scenario_id, request_id)] for request_id in pair_requests) - len(pair_requests) + 1,
                name=f"pair_lb[{scenario_id},{pair_id}]",

    for scenario_id in data["scenario_order"]:

            config["unmet_critical_penalty"]
            * requests[request_id]["critical"]
            * data["scenario_usable"][scenario_id][request_id]
            * (1 - d[(scenario_id, request_id)])

        model.addCons(loss[scenario_id] >= scenarios[scenario_id]["target_profit"] - scenario_profit_expr[scenario_id], name=f"loss_shortfall[{scenario_id}]")
        model.addCons(excess[scenario_id] >= loss[scenario_id] - eta, name=f"cvar_excess[{scenario_id}]")

    expected_profit = quicksum(scenarios[scenario_id]["probability"] * scenario_profit_expr[scenario_id] for scenario_id in data["scenario_order"])

        scenarios[scenario_id]["probability"] * excess[scenario_id] for scenario_id in data["scenario_order"]
    )
    model.setObjective(expected_profit - obs_cost_expr - config["tail_risk_weight"] * cvar_expr, sense="maximize")

    return {
        "model": model,
        "x": x,
        "y": y,
        "z": z,
        "d": d,
        "q": q,
        "b": b,
        "mem": mem,

        "scenario_profit_expr": scenario_profit_expr,
        "obs_cost_expr": obs_cost_expr,
        "cvar_expr": cvar_expr,
    }

            continue
        obs_window = observation_windows[obs_window_id]
        if obs_window["satellite_id"] != contact["satellite_id"]:
            diagnostics["violations"].append(f"Scenario {scenario_id}: request {request_id} downlinked by the wrong satellite.")
            diagnostics["max_residual"] = max(diagnostics["max_residual"], 1.0)
        if obs_window["slot"] >= contact["slot"]:
            diagnostics["violations"].append(f"Scenario {scenario_id}: request {request_id} downlinked before observation.")
            diagnostics["max_residual"] = max(diagnostics["max_residual"], 1.0)
        if contact["slot"] > request["deadline_slot"]:
            diagnostics["violations"].append(f"Scenario {scenario_id}: request {request_id} downlinked after deadline.")
            diagnostics["max_residual"] = max(diagnostics["max_residual"], 1.0)

    for scenario_id in data["scenario_order"]:
        for contact_id, contact in contacts.items():
            used_total = sum(
                downlink_qty[(scenario_id, contact_id, request_id)]
                for request_id in requests
                if (scenario_id, contact_id, request_id) in downlink_qty
            )
            cap = data["scenario_contact_capacity"][(scenario_id, contact_id)]
            residual = max(0.0, used_total - cap)
            if residual > 1e-7:
                diagnostics["violations"].append(f"Scenario {scenario_id}: contact {contact_id} exceeds capacity.")
                diagnostics["max_residual"] = max(diagnostics["max_residual"], residual / max(cap, 1.0))

        for ground_station, station in data["ground_stations"].items():
            for slot in data["horizon_slots"]:
                used = sum(
                    contact_usage.get((scenario_id, contact_id), 0)
                    for contact_id in data["contacts_by_station_slot"].get((ground_station, slot), [])
                )
                excess = used - station["antenna_count"]
                if excess > 0:
                    diagnostics["violations"].append(f"Scenario {scenario_id}: station {ground_station} exceeds antenna count in slot {slot}.")
                    diagnostics["max_residual"] = max(diagnostics["max_residual"], excess / station["antenna_count"])

        for satellite_id in satellites:
            for slot in data["horizon_slots"]:
                obs_used = 1 if any(
                    observation_choice.get(observation_windows[w]["request_id"]) == w
                    for w in data["obs_by_sat_slot"].get((satellite_id, slot), [])
                ) else 0
                dl_used = sat_slot_usage.get((scenario_id, satellite_id, slot), 0)
                if obs_used + dl_used > 1:
                    diagnostics["violations"].append(f"Scenario {scenario_id}: satellite {satellite_id} both observes and downlinks in slot {slot}.")
                    diagnostics["max_residual"] = max(diagnostics["max_residual"], 1.0)

        for region in regions:
            for slot in data["horizon_slots"]:
                used = region_slot_total.get((scenario_id, region, slot), 0.0)
                cap = data["region_ingest"][(scenario_id, region, slot)]
                residual = max(0.0, used - cap)
                if residual > 1e-7:
                    diagnostics["violations"].append(f"Scenario {scenario_id}: region {region} ingest exceeded in slot {slot}.")
                    diagnostics["max_residual"] = max(diagnostics["max_residual"], residual / max(cap, 1.0))

    memory_state = {}
    energy_state = {}
    delivered_value = defaultdict(float)
    downlink_cost = defaultdict(float)
    critical_penalty = defaultdict(float)
    stereo_bonus = defaultdict(float)
    region_delivered = defaultdict(set)
    delivered_critical = defaultdict(int)

    for scenario_id in data["scenario_order"]:
        for request_id, request in requests.items():
            total = sum(
                downlink_qty[(scenario_id, contact_id, request_id)]
                for contact_id in contacts
                if (scenario_id, contact_id, request_id) in downlink_qty
            )
            if data["scenario_usable"][scenario_id][request_id] == 1 and abs(total - request["data_gb"]) <= 1e-6:
                delivered[(scenario_id, request_id)] = 1
                delivered_value[scenario_id] += data["scenario_value"][scenario_id][request_id]
                region_delivered[scenario_id].add(request["disaster_region"])
                if request["critical"] == 1:
                    delivered_critical[scenario_id] += 1
            else:
                delivered[(scenario_id, request_id)] = 0
                if request["critical"] == 1 and data["scenario_usable"][scenario_id][request_id] == 1:
                    critical_penalty[scenario_id] += config["unmet_critical_penalty"]

        for pair_id, pair_requests in stereo_pairs.items():
            if all(delivered[(scenario_id, request_id)] == 1 for request_id in pair_requests):
                stereo_bonus[scenario_id] += config["stereo_pair_bonus"]

        for satellite_id, sat in satellites.items():
            prev_mem = sat["initial_memory_gb"]
            prev_energy = sat["initial_energy_kwh"]
            for slot in data["horizon_slots"]:
                obs_windows = data["obs_by_sat_slot"].get((satellite_id, slot), [])
                obs_add = 0.0
                obs_energy = 0.0
                obs_thermal = 0.0
                for window_id in obs_windows:
                    if observation_choice.get(observation_windows[window_id]["request_id"]) == window_id:
                        request_id = observation_windows[window_id]["request_id"]

                        obs_energy += observation_windows[window_id]["energy_kwh"]
                        obs_thermal += observation_windows[window_id]["thermal_load"]

                    for contact_id in data["contacts_by_sat_slot"].get((satellite_id, slot), [])
                    for request_id in requests
                    if (scenario_id, contact_id, request_id) in downlink_qty

                prev_mem = mem_now

                recharge = max(0.0, recharge)
                energy_now = prev_energy - obs_energy - sat["downlink_energy_kwh_per_gb"] * dl_remove + recharge
                energy_state[(scenario_id, satellite_id, slot)] = energy_now
                prev_energy = energy_now

                mem_residual = max(0.0, -mem_now, mem_now - sat["memory_capacity_gb"])
                if mem_residual > 1e-7:
                    diagnostics["violations"].append(f"Scenario {scenario_id}: memory bound violated for {satellite_id} in slot {slot}.")
                    diagnostics["max_residual"] = max(diagnostics["max_residual"], mem_residual / max(sat["memory_capacity_gb"], 1.0))

                energy_low = max(0.0, config["reserve_energy_kwh"] - energy_now)
                energy_high = max(0.0, energy_now - sat["energy_capacity_kwh"])
                if energy_low > 1e-7 or energy_high > 1e-7:
                    diagnostics["violations"].append(f"Scenario {scenario_id}: energy bound violated for {satellite_id} in slot {slot}.")
                    diagnostics["max_residual"] = max(
                        diagnostics["max_residual"], max(energy_low, energy_high) / max(sat["energy_capacity_kwh"], 1.0)
                    )

            for slot in data["horizon_slots"]:
                start = max(1, slot - data["rolling_window"] + 1)
                thermal_total = 0.0
                for tau in range(start, slot + 1):
                    for window_id in data["obs_by_sat_slot"].get((satellite_id, tau), []):
                        if observation_choice.get(observation_windows[window_id]["request_id"]) == window_id:
                            thermal_total += observation_windows[window_id]["thermal_load"]
                    thermal_total += sat["downlink_thermal_per_gb"] * sum(
                        downlink_qty[(scenario_id, contact_id, request_id)]
                        for contact_id in data["contacts_by_sat_slot"].get((satellite_id, tau), [])
                        for request_id in requests
                        if (scenario_id, contact_id, request_id) in downlink_qty
                    )
                excess = max(0.0, thermal_total - sat["thermal_limit_rolling"])
                if excess > 1e-7:
                    diagnostics["violations"].append(f"Scenario {scenario_id}: thermal limit violated for {satellite_id} ending slot {slot}.")
                    diagnostics["max_residual"] = max(diagnostics["max_residual"], excess / max(sat["thermal_limit_rolling"], 1.0))

        downlink_cost[scenario_id] = config["downlink_cost_per_gb"] * sum(
            qty for (scn, _contact_id, _request_id), qty in downlink_qty.items() if scn == scenario_id
        )

        usable_critical = data["usable_critical_count"][scenario_id]
        if usable_critical > 0:
            achieved = delivered_critical[scenario_id]
            required = config["minimum_critical_delivery_fraction"] * usable_critical
            shortfall = max(0.0, required - achieved)
            if shortfall > 1e-7:
                diagnostics["violations"].append(f"Scenario {scenario_id}: critical delivery floor not met.")
                diagnostics["max_residual"] = max(diagnostics["max_residual"], shortfall / max(usable_critical, 1.0))

        value_required = config["minimum_delivered_value_fraction"] * data["usable_total_value"][scenario_id]
        value_shortfall = max(0.0, value_required - delivered_value[scenario_id])
        if value_shortfall > 1e-7:
            diagnostics["violations"].append(f"Scenario {scenario_id}: delivered value floor not met.")
            diagnostics["max_residual"] = max(
                diagnostics["max_residual"], value_shortfall / max(data["usable_total_value"][scenario_id], 1.0)
            )

        region_shortfall = max(0.0, config["minimum_regions_delivered_per_scenario"] - len(region_delivered[scenario_id]))
        if region_shortfall > 0:
            diagnostics["violations"].append(f"Scenario {scenario_id}: regional coverage floor not met.")
            diagnostics["max_residual"] = max(diagnostics["max_residual"], region_shortfall / max(len(regions), 1))

    observation_cost = config["observation_fixed_cost"] * len(observation_choice)
    scenario_profit = {}
    for scenario_id in data["scenario_order"]:
        scenario_profit[scenario_id] = (
            delivered_value[scenario_id] + stereo_bonus[scenario_id] - downlink_cost[scenario_id] - critical_penalty[scenario_id]
        )
    diagnostics["scenario_profit"] = scenario_profit

    losses = {
        scenario_id: max(0.0, scenarios[scenario_id]["target_profit"] - scenario_profit[scenario_id])
        for scenario_id in data["scenario_order"]
    }
    alpha = config["tail_risk_alpha"]
    candidate_losses = sorted(set(losses.values()))
    best_cvar = None
    for eta in candidate_losses + [0.0]:
        cvar = eta + (1.0 / (1.0 - alpha)) * sum(
            scenarios[scenario_id]["probability"] * max(0.0, losses[scenario_id] - eta) for scenario_id in data["scenario_order"]
        )
        if best_cvar is None or cvar < best_cvar:
            best_cvar = cvar
    expected_profit = sum(scenarios[scenario_id]["probability"] * scenario_profit[scenario_id] for scenario_id in data["scenario_order"])
    objective = expected_profit - observation_cost - config["tail_risk_weight"] * best_cvar
    diagnostics["expected_profit"] = expected_profit
    diagnostics["cvar"] = best_cvar
    diagnostics["objective"] = objective

    diagnostics["incumbent_summary"] = {
        "observations": len(observation_choice),
        "downlink_rows": len(downlink_rows),
        "scenario_deliveries": {
            scenario_id: sum(delivered[(scenario_id, request_id)] for request_id in requests) for scenario_id in data["scenario_order"]
        },
    }
    diagnostics["schema_ok"] = len(diagnostics["violations"]) == 0
    diagnostics["expected_header"] = expected_header
    return diagnostics

def solution_rows_to_maps(data, rows):
    x_values = {window_id: 0.0 for window_id in data["observation_windows"]}
    y_values = defaultdict(float)

    for row in rows:
        if row["row_type"] == "observe":
            key = (row["satellite_id"], int(row["slot"]), row["request_id"])
            window_id = data["observation_lookup"].get(key)
            if window_id is not None:
                x_values[window_id] = 1.0
        elif row["row_type"] == "downlink":
            scenario_id = row["scenario_id"]
            if scenario_id not in data["scenarios"]:
                continue
            contact_key = (row["satellite_id"], int(row["slot"]), row["ground_station"])
            contact_id = data["contact_lookup"].get(contact_key)
            if contact_id is None:
                continue
            request_id = row["request_id"]
            try:
                qty = float(row["quantity"])
            except ValueError:
                continue
            y_values[(scenario_id, contact_id, request_id)] += qty

    delivered = {}
    z_values = {}
    q_values = {}
    b_values = {}
    delivered_by_scenario_region = defaultdict(set)

    delivered_qty = defaultdict(float)
    for (scenario_id, _contact_id, request_id), qty in y_values.items():
        delivered_qty[(scenario_id, request_id)] += qty

    for scenario_id in data["scenario_order"]:
        for request_id, request in data["requests"].items():
            total = delivered_qty[(scenario_id, request_id)]
            delivered[(scenario_id, request_id)] = 1.0 if (
                data["scenario_usable"][scenario_id][request_id] == 1 and abs(total - request["data_gb"]) <= 1e-6
            ) else 0.0
            if delivered[(scenario_id, request_id)] > 0.5:
                delivered_by_scenario_region[scenario_id].add(request["disaster_region"])

        for contact_id in data["contacts"]:
            used = any(
                y_values[(scenario_id, contact_id, request_id)] > data["config"]["quantity_tolerance"]
                for request_id in data["requests"]
            )
            z_values[(scenario_id, contact_id)] = 1.0 if used else 0.0

        for region in data["regions"]:
            q_values[(scenario_id, region)] = 1.0 if region in delivered_by_scenario_region[scenario_id] else 0.0

        for pair_id, pair_requests in data["stereo_pairs"].items():
            b_values[(scenario_id, pair_id)] = 1.0 if all(delivered[(scenario_id, request_id)] > 0.5 for request_id in pair_requests) else 0.0

    return {
        "x_values": x_values,
        "y_values": dict(y_values),
        "d_values": delivered,
        "z_values": z_values,
        "q_values": q_values,
        "b_values": b_values,
    }


def add_mip_start_from_rows(data, model_artifacts, rows):
    model = model_artifacts["model"]
    incumbent = solution_rows_to_maps(data, rows)
    sol = model.createPartialSol()

    for window_id, value in incumbent["x_values"].items():
        model.setSolVal(sol, model_artifacts["x"][window_id], value)

    for key, value in incumbent["y_values"].items():
        if key in model_artifacts["y"]:
            model.setSolVal(sol, model_artifacts["y"][key], value)

    for key, value in incumbent["z_values"].items():
        model.setSolVal(sol, model_artifacts["z"][key], value)

    for key, value in incumbent["d_values"].items():
        model.setSolVal(sol, model_artifacts["d"][key], value)

    for key, value in incumbent["q_values"].items():
        model.setSolVal(sol, model_artifacts["q"][key], value)

    for key, value in incumbent["b_values"].items():
        model.setSolVal(sol, model_artifacts["b"][key], value)

    stored = model.addSol(sol, free=True)
    return stored
