def shortest_path_pair(source, target, road_adj, relevant_set):
    heap = [(0.0, 0, source)]
    best = {source: (0.0, 0)}
    prev = {}
    while heap:
        travel, internal_hits, node = heappop(heap)
        if (travel, internal_hits) != best[node]:
            continue
        if node == target:
            break
        for nxt, edge_time in sorted(road_adj[node].items()):
            new_travel = travel + edge_time
            add_internal = 1 if nxt in relevant_set and nxt not in (source, target) else 0
            new_internal = internal_hits + add_internal
            cand = (new_travel, new_internal)
            if nxt not in best or cand < best[nxt]:
                best[nxt] = cand
                prev[nxt] = node
                heappush(heap, (new_travel, new_internal, nxt))
    if target not in best:
        raise RuntimeError(f"No road path between {source} and {target}")
    path = [target]
    cur = target
    while cur != source:
        cur = prev[cur]
        path.append(cur)
    path.reverse()
    return best[target][0], path

# Flood Relief Multimodal Routing Model

## Modeling choice

The instance is best represented as a **hybrid set-partitioning + optional-route scheduling model**:

- The truck decision is an **optional-node routing problem** on the staging-point network.
- Flooded-shelter boat service is naturally a **set-partitioning problem over feasible boat trips**, because a boat trip serves an ordered subset of shelters from one ramp and the exported artifact must respect the exact listed water arcs.
- Drone decisions are simple **assignment choices** from feasible launch nodes.

A naive arc-flow formulation over truck moves, drone launches, and full boat sequencing would be weak and unnecessarily large. Instead, I preprocess:

1. all-pairs shortest truck travel times between relevant staging points;
2. all feasible single-ramp boat trips that already satisfy capacity and duration;
3. node-level service patterns that combine mandatory dry deliveries with either:
   - a subset of feasible drone launches from that node, or
   - one feasible boat trip from that ramp.

This produces a compact MIP with strong coverage structure and explicit timing.

## Sets and indices

- \(N\): candidate staging points that may host service activity.
- \(D0\): depot.
- \(N^M \subseteq N\): mandatory staging points induced by dry shelters.
- \(N^O = N \setminus N^M\): optional staging points.
- \(H^{dry}\): dry shelters.
- \(H^{fld}\): flooded shelters.
- \(P\): weather periods.
- \(R_i\): feasible service patterns for node \(i \in N\).

Each pattern \(r \in R_i\) is precomputed and contains:

- the set of flooded shelters covered by that pattern, \(F_{ir} \subseteq H^{fld}\);
- whether it is a drone pattern or a boat pattern;
- for each period \(p\), a total stop duration \(dur_{irp}\);
- for each flooded shelter \(h \in F_{ir}\) served by boat, an in-trip service offset \(off_{irph}\) from truck arrival at node \(i\).

Mandatory dry shelters assigned to node \(i\) are denoted by \(M_i \subseteq H^{dry}\).

## Parameters

- \(c_{ij}\): shortest truck travel time from staging point \(i\) to \(j\), computed on the road network.
- \(a_p, b_p\): start and end of weather period \(p\). For the last period, \(b_p\) is treated as \(+\infty\).
- \(d_h\): shelter deadline.
- \(w_h\): shelter priority weight.
- \(\alpha\): lateness penalty per weighted minute.
- \(U\): global time upper bound used in big-\(M\) timing constraints.

Pattern preprocessing uses the public data as follows:

- direct-truck processing at node \(i\):
  \[
  truck\_time_i = 0.18 \cdot \sum_{h \in M_i} demand_h
  \]
- fixed node overhead:
  \[
  base_i = 5 + handling_i
  \]
- drone-trip duration in period \(p\):
  \[
  droneDur_{h i p} = 6 + \mu^{dr}_p \cdot flight_{hi} + 3 \cdot risk_{hi}
  \]
- boat-trip duration in period \(p\):
  \[
  boatDur_{t i p} = 10 + \mu^{bt}_p \cdot waterTravel_{ti} + 4 \cdot |t|
  \]

Boat trips are generated only if they satisfy:

- total boat load \(\le 96\) kg;
- worst-case weather duration using multiplier \(1.12\) is \(\le 115\) minutes;
- every launch-to-first, shelter-to-shelter, and last-to-launch hop is a listed `boat_travel.csv` edge (undirected).

## Decision variables

- \(y_{irp} \in \{0,1\}\): node \(i\) uses service pattern \(r\) and arrives in weather period \(p\).
- \(v_i \in \{0,1\}\): node \(i\) is visited by the truck.
- \(x_{ij} \in \{0,1\}\): truck goes directly from relevant node \(i\) to relevant node \(j\) in the route on the shortest-path closure, where \(i,j \in N \cup \{D0\}\), \(i \ne j\).
- \(A_i \ge 0\): truck arrival time at node \(i\).
- \(D_i \ge 0\): truck departure time from node \(i\).
- \(T_h \ge 0\): service completion time of shelter \(h\).
- \(L_h \ge 0\): lateness of shelter \(h\).
- \(C \ge 0\): truck route completion time at return to depot.

## Objective

Minimize completion time plus weighted lateness:

\[
\min \; C + \alpha \sum_{h \in H^{dry} \cup H^{fld}} w_h L_h
\]

where

\[
L_h \ge T_h - d_h, \quad L_h \ge 0
\]

## Constraints

### 1. Pattern selection and node activation

Mandatory dry-service nodes must choose exactly one active pattern-period pair:

\[
\sum_{r \in R_i} \sum_{p \in P} y_{irp} = 1 \quad \forall i \in N^M
\]

Optional nodes may be unused:

\[
\sum_{r \in R_i} \sum_{p \in P} y_{irp} = v_i \quad \forall i \in N^O
\]

For mandatory nodes, \(v_i = 1\).

### 2. Flooded-shelter coverage

Every flooded shelter is served exactly once by exactly one selected pattern:

\[
\sum_{i \in N} \sum_{r \in R_i : h \in F_{ir}} \sum_{p \in P} y_{irp} = 1
\quad \forall h \in H^{fld}
\]

Dry shelters are fixed to their listed dry node and are automatically served by the selected pattern of that node.

### 3. Weather-period consistency

If pattern-period \((i,r,p)\) is selected, arrival time must lie in that period:

\[
A_i \ge a_p - U(1-y_{irp})
\]
\[
A_i \le b_p + U(1-y_{irp})
\]

For the last period, \(b_p\) is replaced by \(U\).

### 4. Stop duration

Departure equals arrival plus the duration of the selected node pattern:

\[
D_i = A_i + \sum_{r \in R_i} \sum_{p \in P} dur_{irp} \, y_{irp}
\quad \forall i \in N
\]

Inactive optional nodes are forced to zero time:

\[
A_i \le U v_i, \quad D_i \le U v_i \quad \forall i \in N^O
\]

### 5. Truck route degree constraints

Exactly one departure from and one return to the depot:

\[
\sum_{j \in N} x_{D0,j} = 1, \qquad
\sum_{i \in N} x_{i,D0} = 1
\]

Visited nodes have one predecessor and one successor:

\[
\sum_{j \in N \cup \{D0\}\setminus\{i\}} x_{ij} = v_i
\quad \forall i \in N
\]
\[
\sum_{j \in N \cup \{D0\}\setminus\{i\}} x_{ji} = v_i
\quad \forall i \in N
\]

### 6. Truck timing / subtour elimination

From depot to first visited node:

\[
A_j \ge c_{D0,j} - U(1-x_{D0,j})
\quad \forall j \in N
\]

Between visited nodes:

\[
A_j \ge D_i + c_{ij} - U(1-x_{ij})
\quad \forall i,j \in N, i \ne j
\]

Because all travel times and active stop durations are positive, these timing constraints eliminate disconnected subtours.

Completion time on return to depot:

\[
C \ge D_i + c_{i,D0} - U(1-x_{i,D0})
\quad \forall i \in N
\]

### 7. Shelter service-time linking

For every dry shelter \(h \in M_i\):

\[
T_h = D_i
\]

For every flooded shelter \(h\) that is served by a drone pattern at node \(i\):

\[
T_h \ge D_i - U\left(1-\sum_{r \in R_i: h \in F_{ir},\, r \text{ drone}} \sum_{p \in P} y_{irp}\right)
\]
\[
T_h \le D_i + U\left(1-\sum_{r \in R_i: h \in F_{ir},\, r \text{ drone}} \sum_{p \in P} y_{irp}\right)
\]

For every flooded shelter \(h\) served by a boat pattern:

\[
T_h \ge A_i + off_{irph} - U(1-y_{irp})
\]
\[
T_h \le A_i + off_{irph} + U(1-y_{irp})
\]

for each \((i,r,p)\) whose boat pattern contains shelter \(h\).

### 8. Lateness

\[
L_h \ge T_h - d_h, \qquad L_h \ge 0
\quad \forall h
\]

## Export policy

After solving:

1. Recover the selected activity nodes and truck route on the shortest-path closure.
2. Expand each closure arc into the exact road-edge path and write those nodes as `truck_stop` rows.
3. Export:
   - dry shelters as `mode=truck` at their fixed staging point;
   - drone shelters as one row per shelter with its selected launch node;
   - boat shelters in the exact selected trip order with `sequence` inside each trip.

## Explicit assumptions used by the solver

- Truck routing is optimized on shortest-path closure and exported back to direct road edges.
- At most one boat trip is launched from any ramp.
- A ramp stop uses either drone launches or one boat trip, not both.
- Dry-shelter and drone service times are credited at truck departure from the serving node.
- Boat service times are credited along the exported in-trip sequence.
- Weather multipliers are determined by the truck arrival period at the launch node; arrivals after the last listed period use the last period's multiplier.

These assumptions keep the model consistent with the public schema and yield a compact exact MIP for the chosen benchmark interpretation.

                new_load = load + shelters[nxt]["demand_kg"]
                if new_load > float(config["boat_capacity_kg"]) + 1e-9:
                    continue
                if ramp not in boat_adj[nxt]:

                new_water = water_without_return + edge_time

def powerset_nonempty(items):
    items = list(items)
    for r in range(1, len(items) + 1):

            yield subset

def choose_patterns_dp(instance, patterns_by_node):
    flooded = instance["flooded"]
    shelter_index = {shelter_id: idx for idx, shelter_id in enumerate(flooded)}

    nodes = instance["relevant_nodes"]

    pattern_masks = {}
    pattern_cost = {}
    for node in nodes:
        for pattern in patterns_by_node[node]:
            pattern_masks[(node, pattern["pattern_id"])] = pattern_mask(pattern, shelter_index)
            min_duration = min(
                data["duration"] for data in pattern["period_data"].values()
            )
            optional_penalty = 18.0 if node not in mandatory_nodes else 0.0
            pattern_cost[(node, pattern["pattern_id"])] = optional_penalty + min_duration

    dp = {0: (0.0, {})}
    for node in nodes:
        next_dp = {}
        options = list(patterns_by_node[node])
        if node not in mandatory_nodes:
            options = [None] + options
        for mask, (cost, chosen) in dp.items():
            for pattern in options:
                if pattern is None:
                    new_mask = mask
                    new_cost = cost
                    new_choice = chosen
                else:
                    p_mask = pattern_masks[(node, pattern["pattern_id"])]
                    if mask & p_mask:
                        continue
                    new_mask = mask | p_mask
                    new_cost = cost + pattern_cost[(node, pattern["pattern_id"])]
                    new_choice = dict(chosen)
                    new_choice[node] = pattern
                old = next_dp.get(new_mask)
                if old is None or new_cost < old[0] - 1e-9:
                    next_dp[new_mask] = (new_cost, new_choice)
        dp = next_dp

    if full_mask not in dp:
        raise RuntimeError("Pattern DP could not cover all flooded shelters")
    return dp[full_mask][1]


def pattern_candidates_beam(instance, patterns_by_node, beam_width=5):
    flooded = instance["flooded"]

        new_states = {}
        options = list(patterns_by_node[node])
        if node not in mandatory_nodes:
            options = [None] + options
        for mask, entries in states.items():
            for cost, chosen in entries:

                        new_mask = mask

                        new_choice = chosen

                            continue

                        )

                        new_cost = cost + base_cost + optional_penalty
                        new_choice = dict(chosen)
                        new_choice[node] = pattern
                    new_states.setdefault(new_mask, []).append((new_cost, new_choice))
        states = {}
        for mask, entries in new_states.items():
            entries.sort(key=lambda item: item[0])
            kept = []

                key = tuple(sorted((n, p["pattern_id"]) for n, p in chosen.items()))

            states[mask] = kept

    if full_mask not in states:
        raise RuntimeError("Beam search could not cover all flooded shelters")
    return [chosen for _, chosen in states[full_mask]]


def exact_tsp_travel_order(nodes, depot, travel_time):
    if not nodes:
        return []
    indexed = list(nodes)
    n = len(indexed)
    dp = {}
    parent = {}
    for j in range(n):
        mask = 1 << j
        dp[(mask, j)] = travel_time[(depot, indexed[j])]
        parent[(mask, j)] = None
    for mask in range(1, 1 << n):
        for j in range(n):
            if not (mask & (1 << j)):
                continue
            state = (mask, j)
            if state not in dp:
                continue
            for k in range(n):
                if mask & (1 << k):
                    continue
                next_mask = mask | (1 << k)
                cand = dp[state] + travel_time[(indexed[j], indexed[k])]
                next_state = (next_mask, k)
                if next_state not in dp or cand < dp[next_state] - 1e-9:
                    dp[next_state] = cand
                    parent[next_state] = j
    full = (1 << n) - 1
    best_last = min(
        range(n),
        key=lambda j: dp[(full, j)] + travel_time[(indexed[j], depot)],
    )
    order = []
    mask = full
    last = best_last
    while last is not None:
        order.append(indexed[last])
        prev = parent[(mask, last)]
        mask ^= 1 << last
        last = prev
    order.reverse()

## Use when

- The task asks for a Python optimization model using SCIP or `pyscipopt`.
- Existing solver code imports `pyscipopt`, sets SCIP parameters, writes `.lp`/`.mps`, or calls a SCIP-based checker.

def simulate_closure_plan(instance, travel_time, selected_patterns, order):
    config = instance["config"]
    periods = instance["periods"]
    shelters = instance["shelters"]
    depot = config["depot_id"]
    current = depot
    current_time = 0.0
    arrival = {}
    departure = {}
    period_by_node = {}
    service_time = {}

    for node in order:
        current_time += travel_time[(current, node)]
        arr = current_time
        arrival[node] = arr
        period = period_for_time(periods, arr)
        period_by_node[node] = period["id"]
        pattern = selected_patterns[node]
        pdata = pattern["period_data"][period["id"]]
        dep = arr + pdata["duration"]
        departure[node] = dep
        for shelter_id in instance["dry_by_node"].get(node, []):
            service_time[shelter_id] = dep
        for shelter_id in pattern["drone_shelters"]:
            service_time[shelter_id] = dep
        if pattern["kind"] == "boat":
            for shelter_id, offset in pdata["boat_offsets"].items():
                service_time[shelter_id] = arr + offset
        current_time = dep
        current = node

    completion = current_time + travel_time[(current, depot)] if order else 0.0
    weighted_lateness = 0.0
    lateness = {}
    for shelter_id, shelter in shelters.items():
        late = max(0.0, service_time[shelter_id] - shelter["deadline"])
        lateness[shelter_id] = late
        weighted_lateness += shelter["weight"] * late
    objective = completion + float(config["late_penalty_per_weighted_minute"]) * weighted_lateness
    return {
        "arrival": arrival,
        "departure": departure,
        "period_by_node": period_by_node,
        "service_time": service_time,
        "lateness": lateness,
        "completion": completion,
        "objective": objective,
    }

# Optimization Modeling Core

## Use when

- The user gives a word problem, business process, paper scenario, or benchmark prompt and expects a formal optimization model.
- Solver code exists but the issue appears to be a missing or incorrect formulation.
- The task asks for a complete model, not only a heuristic, simulation, or data summary.

## Do not use when

- The task is purely about software plumbing, visualization, data cleaning, or report writing.
- The problem is already fully formulated and the user only asks for code translation into a specific solver; use the solver-specific skill as the primary guide.
- The request is exploratory and the user explicitly wants brainstorming without implementation.

## Model-first workflow

1. Restate the business decision in plain language.
2. Identify sets, indices, units, and time granularity.
3. Extract parameters from data files and confirm units.
4. Define decision variables with domains and business meaning.
5. Write the objective with every cost, reward, penalty, and service term.
6. Write constraints grouped by operational rule.
7. Check edge cases: missing eligibility, impossible demand, fixed commitments, and terminal-state requirements.
8. Only then implement code.

## Ambiguity handling

- If the brief is ambiguous but data and examples imply a convention, state the assumption and continue.
- If ambiguity changes feasibility, objective direction, or deliverable schema, ask before coding or implement the least risky interpretation with a clear note.
- If units conflict across files, normalize units explicitly before modeling.
- If a hard requirement conflicts with data, diagnose the conflict before adding slack variables.

## Formulation checklist

- Every row in an input table should either become a parameter, an eligibility rule, or be explicitly irrelevant.
- Every decision variable should appear in at least one binding constraint and usually in the objective.
- Demand balance should use the correct equality or inequality direction; do not weaken equality to `>=` unless surplus is genuinely allowed.
- Capacity constraints should include activation/open/setup binaries when the business says inactive resources cannot produce, ship, or serve.
- Shortage, backlog, overtime, outsourcing, and postponement variables need explicit cost and bounds.
- Multi-period models need state transition equations and initial/terminal states.
- If the user asks for explanation, describe the modeling logic in business terms after solving.

## Constraint boundary rules

- Hard constraints represent physical impossibility, policy mandates, legal requirements, or explicit benchmark feasibility rules.
- Soft constraints need penalty variables or objective terms; do not silently turn hard constraints into penalties.
- Service levels should specify numerator, denominator, eligible population, and time window.
- Fairness constraints should define the comparison group and whether unavailable resources count.
- Logical implications need both directions only when the business rule says equivalence, not merely implication.

## Objective boundary rules

- Confirm whether the problem minimizes cost, maximizes profit, maximizes service, or uses lexicographic priorities.
- Do not mix penalties with primary economics unless their scale is intentional.
- Include fixed costs only once per activated entity.
- Include revenue only for fulfilled demand or accepted jobs, not for unmet or canceled work.
- Keep reporting metrics separate from optimized objective terms unless the prompt explicitly optimizes them.

## Implementation expectations

- Use structured parsing for CSV/JSON instead of manual string manipulation.
- Keep solver code, solution export, and validation code clearly separated.
- For benchmark or task environments, read the provided brief before coding and follow the expected output schema exactly.
- When comparing two answers, diagnose concrete formulation differences and objective consequences, not only feasibility.
- Write exported solutions at the precision expected by the checker; avoid unnecessary rounding.
- Preserve the input schema and output schema unless the user asks to redesign the benchmark.

## Verification boundary

- Verify feasibility independently from solver status when an evaluator or checker exists.
- Recompute objective from exported artifacts, not only from in-memory solver expressions.
- For benchmark tasks, create at least one negative check for each newly added rule when practical.
- For paper or real-world tasks, separate what is directly supported by the source from synthetic or assumed data.

## Red flags

- Objective terms that are counted twice or charged at the wrong marginal rate.
- Binary variables not linked tightly enough to continuous activity.
- Time periods shifted by one index.
- Average or fairness constraints that ignore the denominator or eligibility set.
- Public prompt files that reveal solver-ready variables or formulas when the benchmark is meant to test modeling translation.
- A feasible solution that exploits missing eligibility, free disposal, negative cycles, or unbounded production.
- A model that reports optimality after a time limit, infeasible status, or missing incumbent.

# Advanced MIP Patterns

## Use when

- The formulation needs logical implications, fixed charges, activation decisions, ordering, no-overlap, disjunctions, min/max, absolute values, tiers, route state, or resource calendars.
- A simple LP/MIP is producing unrealistic behavior because decisions are not linked tightly enough.
- The model is slow or infeasible and the likely cause is weak big-M logic, excessive pairwise variables, or missing state transitions.

## Do not use when

- A continuous LP is sufficient and adding binaries would not represent a real decision.
- The task is better handled by a specialized CP-SAT, constraint programming, nonlinear, or simulation method and the user did not require MIP.
- The user only needs a high-level explanation; do not introduce advanced constructs unless they clarify the actual model.

## General boundary rules

- Add binaries only for real yes/no choices, disjunctions, or nonconvex structure.
- Prefer the tightest formulation that matches the business rule; avoid decorative binaries.
- Use solver-native constructs when they improve clarity and are supported by the target environment.
- If a construct makes the model much slower, compare it with a simpler valid alternative before keeping it.

## Fixed charge and activation

- Use a binary `y` for whether an activity/resource is active.
- Link activity with a tight bound: `x <= U * y`.
- Add lower activation only when the business requires minimum use: `x >= L * y`.
- Charge fixed cost once through `fixed_cost * y`, not per unit.
- Do not force `y = 1` whenever `x = 0` unless the activity is mandatory.
- If there are startup/shutdown costs over time, separate active state from transition state.

## Logical rules

- Prefer solver-native indicator constraints for simple if-then rules when they keep the model clearer.
- If using big-M, derive M from data bounds and keep one M per rule family when possible.
- For either-or choices, use binaries whose sum is exactly one or at most one, matching the business rule.
- Distinguish implication (`A -> B`) from equivalence (`A <-> B`); the reverse direction often needs a separate constraint.
- For conditional capacity, link both activity and resource use to the condition.

## Min, max, absolute value

- For `z = max(a, b)`, add `z >= a`, `z >= b`, and objective pressure if minimizing z. Use binaries only when equality is needed without objective pressure.
- For absolute deviation `d = |x - target|`, add `d >= x - target` and `d >= target - x`.
- For service-level penalties, separate hard feasibility from soft penalty variables.
- For `min`, either transform with signs or add binaries when equality is not enforced by the objective.
- For ratio constraints, cross-multiply only when denominators are constant or safely bounded away from zero.

## Sequencing and no-overlap

- For jobs sharing a resource, use order binary `before[i,j]`.
- Typical pattern:
  - `start[j] >= end[i] - M * (1 - before[i,j])`
  - `start[i] >= end[j] - M * before[i,j]`
- Compute M from the scheduling horizon, not from an arbitrary large number.
- Include setup, cleanup, travel, rest, or turnover time in the correct side of the ordering constraint.
- Create pairwise order variables only for pairs that can share a resource or conflict.
- If time is discrete and the horizon is small, a time-indexed model may be cleaner than pairwise disjunctions.

## Piecewise and tiers

- Use solver-native piecewise-linear features for convex piecewise costs when suitable.
- For nonconvex tiers, use explicit segment variables and segment activation binaries.
- Ensure tier quantities sum to the original activity and each tier has its own upper bound.
- Distinguish incremental tiers from all-units tiers; their formulations and costs differ.
- Check whether discount tiers create nonconvex incentives that require binary selection.

## State and inventory logic

- State variables need initial conditions, transition equations, and terminal requirements if the business specifies them.
- Route or schedule state should be advanced in event order, not checked only row by row.
- Recovery, restock, cleaning, cooldown, maintenance, and rest rules often require cumulative state or last-event logic.
- If state can reset, model the reset trigger and its resource/time cost.

## Debugging advanced models

- First solve a relaxed or smaller instance and inspect whether the intended binaries activate.
- Add named constraints so IIS output points to business rules.
- If the reference solution is infeasible, replay the relevant state transitions manually before changing the evaluator.
- If the LP relaxation is very weak, inspect big-M values, missing lower/upper links, and symmetry.
- If the model is unexpectedly infeasible, test each advanced rule family on a tiny instance with a known feasible solution.

# Flood Relief Multimodal Routing Model

## Modeling choice

The instance is best represented as a **hybrid set-partitioning + optional-route scheduling model**:

- The truck decision is an **optional-node routing problem** on the staging-point network.
- Flooded-shelter boat service is naturally a **set-partitioning problem over feasible boat trips**, because a boat trip serves an ordered subset of shelters from one ramp and the exported artifact must respect the exact listed water arcs.
- Drone decisions are simple **assignment choices** from feasible launch nodes.

A naive arc-flow formulation over truck moves, drone launches, and full boat sequencing would be weak and unnecessarily large. Instead, I preprocess:

1. all-pairs shortest truck travel times between relevant staging points;
2. all feasible single-ramp boat trips that already satisfy capacity and duration;
3. node-level service patterns that combine mandatory dry deliveries with either:
   - a subset of feasible drone launches from that node, or
   - one feasible boat trip from that ramp.

This produces a compact MIP with strong coverage structure and explicit timing.

## Sets and indices

- \(N\): candidate staging points that may host service activity.
- \(D0\): depot.
- \(N^M \subseteq N\): mandatory staging points induced by dry shelters.
- \(N^O = N \setminus N^M\): optional staging points.
- \(H^{dry}\): dry shelters.
- \(H^{fld}\): flooded shelters.
- \(P\): weather periods.
- \(R_i\): feasible service patterns for node \(i \in N\).

Each pattern \(r \in R_i\) is precomputed and contains:

- the set of flooded shelters covered by that pattern, \(F_{ir} \subseteq H^{fld}\);
- whether it is a drone pattern or a boat pattern;
- for each period \(p\), a total stop duration \(dur_{irp}\);
- for each flooded shelter \(h \in F_{ir}\) served by boat, an in-trip service offset \(off_{irph}\) from truck arrival at node \(i\).

Mandatory dry shelters assigned to node \(i\) are denoted by \(M_i \subseteq H^{dry}\).

def shortest_path_pair(source, target, road_adj, relevant_set):
    heap = [(0.0, 0, source)]
    best = {source: (0.0, 0)}
    prev = {}
    while heap:
        travel, internal_hits, node = heappop(heap)
        if (travel, internal_hits) != best[node]:
            continue
        if node == target:
            break
        for nxt, edge_time in sorted(road_adj[node].items()):
            new_travel = travel + edge_time
            add_internal = 1 if nxt in relevant_set and nxt not in (source, target) else 0
            new_internal = internal_hits + add_internal
            cand = (new_travel, new_internal)
            if nxt not in best or cand < best[nxt]:
                best[nxt] = cand
                prev[nxt] = node
                heappush(heap, (new_travel, new_internal, nxt))
    if target not in best:
        raise RuntimeError(f"No road path between {source} and {target}")
    path = [target]
    cur = target
    while cur != source:
        cur = prev[cur]
        path.append(cur)
    path.reverse()
    return best[target][0], path

# OR PySCIPOpt

## Use when

- The task asks for a Python optimization model using SCIP or `pyscipopt`.
- Existing solver code imports `pyscipopt`, sets SCIP parameters, writes `.lp`/`.mps`, or calls a SCIP-based checker.
- The user asks to run, debug, speed up, validate, or explain a SCIP-based solve.

- The task only needs a mathematical formulation and no solver-specific code.
- The project clearly uses a different solver stack, such as Pyomo with CBC/HiGHS, OR-Tools CP-SAT, PuLP, CPLEX, or cvxpy, unless the user asks to port it to PySCIPOpt.
- The model is nonlinear or stochastic in a way that SCIP cannot handle directly; first decide whether it can be linearized or approximated.

- Use `from pyscipopt import Model, quicksum`.
- Create sparse variable dictionaries explicitly, for example:

def pattern_mask(pattern, shelter_index):
    mask = 0
    for shelter_id in pattern["flooded_covered"]:
        mask |= 1 << shelter_index[shelter_id]

def choose_patterns_dp(instance, patterns_by_node):

    pattern_cost = {}
    for node in nodes:
        for pattern in patterns_by_node[node]:
            pattern_masks[(node, pattern["pattern_id"])] = pattern_mask(pattern, shelter_index)
            min_duration = min(
                data["duration"] for data in pattern["period_data"].values()
            )
            optional_penalty = 18.0 if node not in mandatory_nodes else 0.0
            pattern_cost[(node, pattern["pattern_id"])] = optional_penalty + min_duration

    dp = {0: (0.0, {})}
    for node in nodes:
        next_dp = {}
        options = list(patterns_by_node[node])
        if node not in mandatory_nodes:
            options = [None] + options
        for mask, (cost, chosen) in dp.items():
            for pattern in options:
                if pattern is None:
                    new_mask = mask
                    new_cost = cost
                    new_choice = chosen
                else:
                    p_mask = pattern_masks[(node, pattern["pattern_id"])]
                    if mask & p_mask:
                        continue

                    new_cost = cost + pattern_cost[(node, pattern["pattern_id"])]
                    new_choice = dict(chosen)

                    next_dp[new_mask] = (new_cost, new_choice)
        dp = next_dp

    if full_mask not in dp:
        raise RuntimeError("Pattern DP could not cover all flooded shelters")
    return dp[full_mask][1]

                        new_cost = cost + base_cost + optional_penalty

        raise RuntimeError("Beam search could not cover all flooded shelters")
