# Optimization Modeling Core

## Use when

- The user gives a word problem, business process, paper scenario, or benchmark prompt and expects a formal optimization model.
- Solver code exists but the issue appears to be a missing or incorrect formulation.
- The task asks for a complete model, not only a heuristic, simulation, or data summary.

## Do not use when

- The task is purely about software plumbing, visualization, data cleaning, or report writing.
- The problem is already fully formulated and the user only asks for code translation into a specific solver; use the solver-specific skill as the primary guide.
- The request is exploratory and the user explicitly wants brainstorming without implementation.

## Model-first workflow

1. Restate the business decision in plain language.
2. Identify sets, indices, units, and time granularity.
3. Extract parameters from data files and confirm units.
4. Define decision variables with domains and business meaning.
5. Write the objective with every cost, reward, penalty, and service term.
6. Write constraints grouped by operational rule.
7. Check edge cases: missing eligibility, impossible demand, fixed commitments, and terminal-state requirements.
8. Only then implement code.

## Ambiguity handling

- If the brief is ambiguous but data and examples imply a convention, state the assumption and continue.
- If ambiguity changes feasibility, objective direction, or deliverable schema, ask before coding or implement the least risky interpretation with a clear note.
- If units conflict across files, normalize units explicitly before modeling.
- If a hard requirement conflicts with data, diagnose the conflict before adding slack variables.

## Formulation checklist

- Every row in an input table should either become a parameter, an eligibility rule, or be explicitly irrelevant.
- Every decision variable should appear in at least one binding constraint and usually in the objective.
- Demand balance should use the correct equality or inequality direction; do not weaken equality to `>=` unless surplus is genuinely allowed.
- Capacity constraints should include activation/open/setup binaries when the business says inactive resources cannot produce, ship, or serve.
- Shortage, backlog, overtime, outsourcing, and postponement variables need explicit cost and bounds.
- Multi-period models need state transition equations and initial/terminal states.
- If the user asks for explanation, describe the modeling logic in business terms after solving.

## Constraint boundary rules

- Hard constraints represent physical impossibility, policy mandates, legal requirements, or explicit benchmark feasibility rules.
- Soft constraints need penalty variables or objective terms; do not silently turn hard constraints into penalties.
- Service levels should specify numerator, denominator, eligible population, and time window.
- Fairness constraints should define the comparison group and whether unavailable resources count.
- Logical implications need both directions only when the business rule says equivalence, not merely implication.

## Objective boundary rules

- Confirm whether the problem minimizes cost, maximizes profit, maximizes service, or uses lexicographic priorities.
- Do not mix penalties with primary economics unless their scale is intentional.
- Include fixed costs only once per activated entity.
- Include revenue only for fulfilled demand or accepted jobs, not for unmet or canceled work.
- Keep reporting metrics separate from optimized objective terms unless the prompt explicitly optimizes them.

## Implementation expectations

- Use structured parsing for CSV/JSON instead of manual string manipulation.
- Keep solver code, solution export, and validation code clearly separated.
- For benchmark or task environments, read the provided brief before coding and follow the expected output schema exactly.
- When comparing two answers, diagnose concrete formulation differences and objective consequences, not only feasibility.
- Write exported solutions at the precision expected by the checker; avoid unnecessary rounding.
- Preserve the input schema and output schema unless the user asks to redesign the benchmark.

## Verification boundary

- Verify feasibility independently from solver status when an evaluator or checker exists.
- Recompute objective from exported artifacts, not only from in-memory solver expressions.
- For benchmark tasks, create at least one negative check for each newly added rule when practical.
- For paper or real-world tasks, separate what is directly supported by the source from synthetic or assumed data.

## Red flags

- Objective terms that are counted twice or charged at the wrong marginal rate.
- Binary variables not linked tightly enough to continuous activity.
- Time periods shifted by one index.
- Average or fairness constraints that ignore the denominator or eligibility set.
- Public prompt files that reveal solver-ready variables or formulas when the benchmark is meant to test modeling translation.
- A feasible solution that exploits missing eligibility, free disposal, negative cycles, or unbounded production.
- A model that reports optimality after a time limit, infeasible status, or missing incumbent.

# Advanced MIP Patterns

## Use when

- The formulation needs logical implications, fixed charges, activation decisions, ordering, no-overlap, disjunctions, min/max, absolute values, tiers, route state, or resource calendars.
- A simple LP/MIP is producing unrealistic behavior because decisions are not linked tightly enough.
- The model is slow or infeasible and the likely cause is weak big-M logic, excessive pairwise variables, or missing state transitions.

## Do not use when

- A continuous LP is sufficient and adding binaries would not represent a real decision.
- The task is better handled by a specialized CP-SAT, constraint programming, nonlinear, or simulation method and the user did not require MIP.
- The user only needs a high-level explanation; do not introduce advanced constructs unless they clarify the actual model.

## General boundary rules

- Add binaries only for real yes/no choices, disjunctions, or nonconvex structure.
- Prefer the tightest formulation that matches the business rule; avoid decorative binaries.
- Use solver-native constructs when they improve clarity and are supported by the target environment.
- If a construct makes the model much slower, compare it with a simpler valid alternative before keeping it.

## Fixed charge and activation

- Use a binary `y` for whether an activity/resource is active.
- Link activity with a tight bound: `x <= U * y`.
- Add lower activation only when the business requires minimum use: `x >= L * y`.
- Charge fixed cost once through `fixed_cost * y`, not per unit.
- Do not force `y = 1` whenever `x = 0` unless the activity is mandatory.
- If there are startup/shutdown costs over time, separate active state from transition state.

## Logical rules

- Prefer solver-native indicator constraints for simple if-then rules when they keep the model clearer.
- If using big-M, derive M from data bounds and keep one M per rule family when possible.
- For either-or choices, use binaries whose sum is exactly one or at most one, matching the business rule.
- Distinguish implication (`A -> B`) from equivalence (`A <-> B`); the reverse direction often needs a separate constraint.
- For conditional capacity, link both activity and resource use to the condition.

## Min, max, absolute value

- For `z = max(a, b)`, add `z >= a`, `z >= b`, and objective pressure if minimizing z. Use binaries only when equality is needed without objective pressure.
- For absolute deviation `d = |x - target|`, add `d >= x - target` and `d >= target - x`.
- For service-level penalties, separate hard feasibility from soft penalty variables.
- For `min`, either transform with signs or add binaries when equality is not enforced by the objective.
- For ratio constraints, cross-multiply only when denominators are constant or safely bounded away from zero.

## Sequencing and no-overlap

- For jobs sharing a resource, use order binary `before[i,j]`.
- Typical pattern:
  - `start[j] >= end[i] - M * (1 - before[i,j])`
  - `start[i] >= end[j] - M * before[i,j]`
- Compute M from the scheduling horizon, not from an arbitrary large number.
- Include setup, cleanup, travel, rest, or turnover time in the correct side of the ordering constraint.
- Create pairwise order variables only for pairs that can share a resource or conflict.
- If time is discrete and the horizon is small, a time-indexed model may be cleaner than pairwise disjunctions.

## Piecewise and tiers

- Use solver-native piecewise-linear features for convex piecewise costs when suitable.
- For nonconvex tiers, use explicit segment variables and segment activation binaries.
- Ensure tier quantities sum to the original activity and each tier has its own upper bound.
- Distinguish incremental tiers from all-units tiers; their formulations and costs differ.
- Check whether discount tiers create nonconvex incentives that require binary selection.

## State and inventory logic

- State variables need initial conditions, transition equations, and terminal requirements if the business specifies them.
- Route or schedule state should be advanced in event order, not checked only row by row.
- Recovery, restock, cleaning, cooldown, maintenance, and rest rules often require cumulative state or last-event logic.
- If state can reset, model the reset trigger and its resource/time cost.

## Debugging advanced models

- First solve a relaxed or smaller instance and inspect whether the intended binaries activate.
- Add named constraints so IIS output points to business rules.
- If the reference solution is infeasible, replay the relevant state transitions manually before changing the evaluator.
- If the LP relaxation is very weak, inspect big-M values, missing lower/upper links, and symmetry.
- If the model is unexpectedly infeasible, test each advanced rule family on a tiny instance with a known feasible solution.

capacity is chosen by supplier and item using
`data/supplier_item_capacity.csv`; incompatible pairs have zero available
capacity. Reserved capacity is paid for before the scenario is known and is
limited by supplier activation, item compatibility, and supplier line-hours.

Initial stock is chosen by warehouse and item. It is paid for before the
scenario is known, consumes storage volume, and cannot exceed the item-specific
warehouse limit. Cold-chain items can be stocked only in cold-chain warehouses.
The activation, starting-stock, and reserved-capacity spend must respect the
planning budget in `data/config.json`.

## Scenario-Period Recourse

Each scenario in `data/scenarios.csv` has a probability and represents one
possible disruption family. Demand is listed in
`data/scenario_period_demands.csv` by scenario, day, clinic, and item. For each
scenario-day-clinic-item combination, delivered quantities, local emergency
purchases, and unmet demand must account for the full demand.

Production is adaptive to the realized scenario. A supplier can produce only
items for which capacity was reserved. Actual day capacity is adjusted by
`data/scenario_period_supplier_availability.csv`. Production also carries
line-start rules from `data/suppliers.csv` and
`data/supplier_item_capacity.csv`: a supplier can run only a limited number of
item lines per day, a positive run must clear the item-specific minimum batch,
and setup hours count against the same disrupted line-hour pool as unit
production. Produced supply must be sent to warehouses over listed
supplier-warehouse lanes and must respect scenario lane capacities in
`data/scenario_period_supplier_lane_impacts.csv`.

Warehouse inventory is tracked separately for each scenario. Starting stock is
available at the beginning of the first day. New inbound receipts may have an
item-specific release lag in `data/items.csv`; the antiviral supply, for
example, must pass cold-chain quality release before it can be dispatched from
the warehouse on a later day. Quarantined receipts still consume warehouse
storage while they wait for release. Warehouse storage and outbound handling
are adjusted by
`data/scenario_period_warehouse_availability.csv`. Oxygen uses returnable
cylinders: a fraction of oxygen delivered from a warehouse returns after the
configured lag and can be shipped again in later days.

Clinic deliveries may use only listed warehouse-clinic lanes in
`data/warehouse_clinic_lanes.csv`. Day-specific road impacts in
`data/scenario_period_road_impacts.csv` adjust lane capacity, travel time, and
extra transport cost. Cold-chain items must use cold-chain-capable fleets.
Badly disrupted road periods may require high-clearance or airlift fleets, and
non-airlift fleets cannot exceed their maximum travel-time limit. Fleet
availability is listed in `data/warehouse_fleet.csv`.

Emergency purchases are allowed but limited by both
`data/scenario_expedite_caps.csv` and each clinic's local purchase fraction.
Unmet demand is allowed but expensive and cannot bypass the service floors.

## Service, Equity, And Receiving Rules

Every clinic has final service floors by item in `data/clinics.csv`. The
cumulative delivered-plus-emergency-purchased amount must meet the appropriate
fraction of those final floors after each day using `data/service_targets.csv`.
Critical clinics cannot be left far behind easier clinics: for each scenario
and item, a critical clinic's final fill rate may not be more than the
configured fairness gap below any non-critical clinic's fill rate.

Each clinic has a daily receiving-capacity limit. Cold-chain emergency purchase
and delivered antiviral quantities also count against the clinic's cold
storage capacity.

# Advanced MIP Patterns

## Use when

- The formulation needs logical implications, fixed charges, activation decisions, ordering, no-overlap, disjunctions, min/max, absolute values, tiers, route state, or resource calendars.
- A simple LP/MIP is producing unrealistic behavior because decisions are not linked tightly enough.
- The model is slow or infeasible and the likely cause is weak big-M logic, excessive pairwise variables, or missing state transitions.

## Do not use when

- A continuous LP is sufficient and adding binaries would not represent a real decision.
- The task is better handled by a specialized CP-SAT, constraint programming, nonlinear, or simulation method and the user did not require MIP.
- The user only needs a high-level explanation; do not introduce advanced constructs unless they clarify the actual model.

## General boundary rules

- Add binaries only for real yes/no choices, disjunctions, or nonconvex structure.
- Prefer the tightest formulation that matches the business rule; avoid decorative binaries.
- Use solver-native constructs when they improve clarity and are supported by the target environment.
- If a construct makes the model much slower, compare it with a simpler valid alternative before keeping it.

## Fixed charge and activation

- Use a binary `y` for whether an activity/resource is active.
- Link activity with a tight bound: `x <= U * y`.
- Add lower activation only when the business requires minimum use: `x >= L * y`.
- Charge fixed cost once through `fixed_cost * y`, not per unit.
- Do not force `y = 1` whenever `x = 0` unless the activity is mandatory.
- If there are startup/shutdown costs over time, separate active state from transition state.

## Logical rules

- Prefer solver-native indicator constraints for simple if-then rules when they keep the model clearer.
- If using big-M, derive M from data bounds and keep one M per rule family when possible.
- For either-or choices, use binaries whose sum is exactly one or at most one, matching the business rule.
- Distinguish implication (`A -> B`) from equivalence (`A <-> B`); the reverse direction often needs a separate constraint.
- For conditional capacity, link both activity and resource use to the condition.

## Min, max, absolute value

- For `z = max(a, b)`, add `z >= a`, `z >= b`, and objective pressure if minimizing z. Use binaries only when equality is needed without objective pressure.
- For absolute deviation `d = |x - target|`, add `d >= x - target` and `d >= target - x`.
- For service-level penalties, separate hard feasibility from soft penalty variables.
- For `min`, either transform with signs or add binaries when equality is not enforced by the objective.
- For ratio constraints, cross-multiply only when denominators are constant or safely bounded away from zero.

## Sequencing and no-overlap

- For jobs sharing a resource, use order binary `before[i,j]`.
- Typical pattern:
  - `start[j] >= end[i] - M * (1 - before[i,j])`
  - `start[i] >= end[j] - M * before[i,j]`
- Compute M from the scheduling horizon, not from an arbitrary large number.
- Include setup, cleanup, travel, rest, or turnover time in the correct side of the ordering constraint.
- Create pairwise order variables only for pairs that can share a resource or conflict.
- If time is discrete and the horizon is small, a time-indexed model may be cleaner than pairwise disjunctions.

## Piecewise and tiers

- Use solver-native piecewise-linear features for convex piecewise costs when suitable.
- For nonconvex tiers, use explicit segment variables and segment activation binaries.
- Ensure tier quantities sum to the original activity and each tier has its own upper bound.
- Distinguish incremental tiers from all-units tiers; their formulations and costs differ.
- Check whether discount tiers create nonconvex incentives that require binary selection.

## State and inventory logic

- State variables need initial conditions, transition equations, and terminal requirements if the business specifies them.
- Route or schedule state should be advanced in event order, not checked only row by row.
- Recovery, restock, cleaning, cooldown, maintenance, and rest rules often require cumulative state or last-event logic.
- If state can reset, model the reset trigger and its resource/time cost.

## Debugging advanced models

- First solve a relaxed or smaller instance and inspect whether the intended binaries activate.
- Add named constraints so IIS output points to business rules.
- If the reference solution is infeasible, replay the relevant state transitions manually before changing the evaluator.
- If the LP relaxation is very weak, inspect big-M values, missing lower/upper links, and symmetry.
- If the model is unexpectedly infeasible, test each advanced rule family on a tiny instance with a known feasible solution.

                    )

                for w in data["supplier_wh_by_supplier"][s]:
                    lane_keys = data["inbound_by_lane"].get((omega, period, s, w), [])
                    if not lane_keys:
                        continue
                    model.addCons(
                        quicksum(items[key[4]]["load_factor"] * inbound[key] for key in lane_keys)
                        <= supplier_wh[(s, w)]["base_capacity"]
                        * data["supplier_lane_impact"][(omega, period, s, w)][
                            "capacity_multiplier"
                        ],
                        name=f"sw_lane_cap[{omega},{period},{s},{w}]",
                    )

            for w in data["warehouse_ids"]:
                wh_state = data["warehouse_availability"][(omega, period, w)]
                p_idx = data["period_index"][period]
                prev_p = data["prev_period"][period]
                for item in data["item_ids"]:
                    lag = items[item]["release_lag"]
                    if lag == 0:
                        model.addCons(
                            quarantine[(omega, period, w, item)] == 0.0,
                            name=f"quar_zero[{omega},{period},{w},{item}]",
                        )
                        released_expr = quicksum(
                            inbound[key]
                            for key in data["inbound_to_wh_item"].get(
                                (omega, period, w, item), []
                            )
                        )
                    else:
                        start = max(0, p_idx - lag + 1)
                        model.addCons(
                            quarantine[(omega, period, w, item)]
                            == quicksum(
                                inbound[key]
                                for idx in range(start, p_idx + 1)
                                for key in data["inbound_to_wh_item"].get(
                                    (omega, data["period_ids"][idx], w, item), []
                                )
                            ),
                            name=f"quar_def[{omega},{period},{w},{item}]",
                        )
                        rel_idx = p_idx - lag
                        released_expr = (
                            quicksum(
                                inbound[key]
                                for key in data["inbound_to_wh_item"].get(
                                    (omega, data["period_ids"][rel_idx], w, item), []
                                )
                            )
                            if rel_idx >= 0
                            else 0.0
                        )

                    dispatch_expr = quicksum(
                        dispatch[key]
                        for key in data["dispatch_by_wh_item"].get((omega, period, w, item), [])
                    )
                    if item == "oxygen":
                        ret_idx = p_idx - int(config["oxygen_return_lag_periods"])
                        return_expr = (
                            config["oxygen_return_fraction"]
                            * quicksum(
                                dispatch[key]
                                for key in data["dispatch_by_wh_item"].get(
                                    (omega, data["period_ids"][ret_idx], w, item), []
                                )
                            )
                            if ret_idx >= 0
                            else 0.0
                        )
                    else:
                        return_expr = 0.0

                    rhs = stock[(w, item)] + released_expr + return_expr - dispatch_expr
                    if prev_p is not None:
                        rhs = inventory[(omega, prev_p, w, item)] + released_expr + return_expr - dispatch_expr
                    model.addCons(
                        inventory[(omega, period, w, item)] == rhs,
                        name=f"inv_bal[{omega},{period},{w},{item}]",
                    )
                    if items[item]["cold_chain_required"] and not warehouses[w]["cold_chain"]:
                        model.addCons(
                            inventory[(omega, period, w, item)] == 0.0,
                            name=f"inv_cold[{omega},{period},{w},{item}]",
                        )
                        model.addCons(
                            quarantine[(omega, period, w, item)] == 0.0,
                            name=f"quar_cold[{omega},{period},{w},{item}]",
                        )

                model.addCons(
                    quicksum(
                        items[item]["load_factor"] * dispatch[key]
                        for item in data["item_ids"]
                        for key in data["dispatch_by_wh_item"].get((omega, period, w, item), [])
                    )
                    <= warehouses[w]["outbound_capacity"]
                    * wh_state["outbound_multiplier"]
                    * y_open[w],
                    name=f"wh_outbound[{omega},{period},{w}]",
                )
                model.addCons(
                    quicksum(
                        items[item]["unit_volume"]
                        * (
                            inventory[(omega, period, w, item)]
                            + quarantine[(omega, period, w, item)]
                        )
                        for item in data["item_ids"]
                    )
                    <= warehouses[w]["storage_capacity"]
                    * wh_state["storage_multiplier"]
                    * y_open[w],
                    name=f"wh_storage[{omega},{period},{w}]",
                )

            for c in data["clinic_ids"]:
                for item in data["item_ids"]:
                    delivered = quicksum(
                        dispatch[key]
                        for key in data["dispatch_by_demand"].get((omega, period, c, item), [])
                    )
                    service_today = delivered + expedite[(omega, period, c, item)]
                    model.addCons(
                        service_today + unmet[(omega, period, c, item)]
                        == data["demand"][(omega, period, c, item)],
                        name=f"demand[{omega},{period},{c},{item}]",
                    )
                    if data["prev_period"][period] is None:
                        model.addCons(
                            served_cum[(omega, period, c, item)] == service_today,
                            name=f"served_init[{omega},{period},{c},{item}]",
                        )
                    else:
                        model.addCons(
                            served_cum[(omega, period, c, item)]
                            == served_cum[(omega, data["prev_period"][period], c, item)]
                            + service_today,
                            name=f"served_step[{omega},{period},{c},{item}]",
                        )
                    model.addCons(
                        served_cum[(omega, period, c, item)]
                        >= data["cumulative_floor_req"][(omega, period, c, item)],
                        name=f"service_floor[{omega},{period},{c},{item}]",
                    )

                model.addCons(
                    quicksum(
                        items[item]["unit_volume"]
                        * (
                            quicksum(
                                dispatch[key]
                                for key in data["dispatch_by_demand"].get(
                                    (omega, period, c, item), []
                                )
                            )
                            + expedite[(omega, period, c, item)]
                        )
                        for item in data["item_ids"]
                    )
                    <= clinics[c]["receiving_capacity"],
                    name=f"receive_cap[{omega},{period},{c}]",
                )
                model.addCons(
                    quicksum(
                        items[item]["unit_volume"]
                        * (
                            quicksum(
                                dispatch[key]
                                for key in data["dispatch_by_demand"].get(
                                    (omega, period, c, item), []
                                )
                            )
                            + expedite[(omega, period, c, item)]
                        )
                        for item in data["cold_items"]
                    )
                    <= clinics[c]["cold_storage_capacity"],
                    name=f"cold_cap[{omega},{period},{c}]",
                )

            for w in data["warehouse_ids"]:
                for c in data["wh_clinic_by_warehouse"][w]:
                    lane_keys = data["dispatch_by_lane"].get((omega, period, w, c), [])
                    if lane_keys:
                        model.addCons(
                            quicksum(items[key[4]]["load_factor"] * dispatch[key] for key in lane_keys)
                            <= wh_clinic[(w, c)]["base_capacity"]
                            * data["road_impact"][(omega, period, w, c)]["capacity_multiplier"],
                            name=f"road_cap[{omega},{period},{w},{c}]",
                        )
                for fleet in data["fleet_ids"]:
                    fleet_keys = data["dispatch_by_wh_fleet"].get((omega, period, w, fleet), [])
                    if fleet_keys:
                        model.addCons(
                            quicksum(
                                items[key[4]]["load_factor"]
                                / fleets[fleet]["capacity_load"]
                                * dispatch[key]
                                for key in fleet_keys
                            )
                            <= data["warehouse_fleet"][(w, period, fleet)] * y_open[w],
                            name=f"fleet_cap[{omega},{period},{w},{fleet}]",
                        )

        for item in data["item_ids"]:
            model.addCons(
                quicksum(
                    expedite[(omega, period, c, item)]
                    for period in data["period_ids"]
                    for c in data["clinic_ids"]
                )
                <= data["expedite_caps"][(omega, item)],
                name=f"exp_cap[{omega},{item}]",
            )

        last_period = data["period_ids"][-1]
        for item in data["item_ids"]:
            for c_crit in data["critical_clinics"]:
                for c_other in data["noncritical_clinics"]:
                    total_crit = data["demand_by_sci"][(omega, c_crit, item)]
                    total_other = data["demand_by_sci"][(omega, c_other, item)]
                    model.addCons(
                        total_other * served_cum[(omega, last_period, c_crit, item)]
                        - total_crit * served_cum[(omega, last_period, c_other, item)]
                        >= -config["fairness_gap"] * total_crit * total_other,
                        name=f"fair[{omega},{item},{c_crit},{c_other}]",
                    )

    for omega in data["scenario_ids"]:
        expr = quicksum(
            items[key[3]]["production_cost"] * produce[key]
            + supplier_item[(key[2], key[3])]["setup_cost"] * run[key]
            for key in data["prod_keys"]
            if key[0] == omega
        )
        expr += quicksum(
            supplier_wh[(key[2], key[3])]["transport_cost_per_load"]
            * data["supplier_lane_impact"][(key[0], key[1], key[2], key[3])]["cost_multiplier"]
            * items[key[4]]["load_factor"]
            * inbound[key]
            for key in data["inbound_keys"]
            if key[0] == omega
        )
        expr += quicksum(
            (
                wh_clinic[(key[2], key[3])]["transport_cost_per_load"]
                + data["road_impact"][(key[0], key[1], key[2], key[3])][
                    "extra_transport_cost_per_load"
                ]
            )
            * items[key[4]]["load_factor"]
            * dispatch[key]
            for key in data["dispatch_keys"]
            if key[0] == omega
        )
        expr += quicksum(
            fleets[key[5]]["fixed_trip_cost"]
            * items[key[4]]["load_factor"]
            / fleets[key[5]]["capacity_load"]
            * dispatch[key]
            for key in data["dispatch_keys"]
            if key[0] == omega
        )
        expr += quicksum(
            config["late_response_penalty_per_load_hour"]
            * periods[key[1]]["delay_multiplier"]
            * data["road_impact"][(key[0], key[1], key[2], key[3])]["travel_time_hours"]
            * items[key[4]]["load_factor"]
            * dispatch[key]
            for key in data["dispatch_keys"]
            if key[0] == omega
        )
        expr += quicksum(
            items[key[3]]["expedite_cost"] * expedite[key]
            + items[key[3]]["shortage_penalty"] * unmet[key]
            for key in expedite
            if key[0] == omega
        )
        expr += quicksum(
            items[key[3]]["holding_cost"] * (inventory[key] + quarantine[key])
            for key in inventory
            if key[0] == omega
        )
        model.addCons(op_cost[omega] == expr, name=f"opcost_def[{omega}]")
        model.addCons(cvar_excess[omega] >= op_cost[omega] - eta, name=f"cvar[{omega}]")
        model.addCons(
            amb_lam + amb_alpha[omega] - amb_beta[omega] >= op_cost[omega],
            name=f"amb1[{omega}]",
        )
        model.addCons(
            amb_gamma >= amb_alpha[omega] + amb_beta[omega],
            name=f"amb2[{omega}]",
        )

    worst_case_expected = amb_lam + quicksum(
        scenarios[omega]["probability"] * (amb_alpha[omega] - amb_beta[omega])
        for omega in data["scenario_ids"]
    ) + config["ambiguity_radius"] * amb_gamma
    cvar_term = eta + (1.0 / (1.0 - config["tail_risk_alpha"])) * quicksum(
        scenarios[omega]["probability"] * cvar_excess[omega]
        for omega in data["scenario_ids"]
    )

    model.setObjective(
        first_stage_cost + worst_case_expected + config["tail_risk_weight"] * cvar_term,
        "minimize",
    )

    return model, {
        "y_open": y_open,
        "y_active": y_active,
        "stock": stock,
        "reserve": reserve,
        "run": run,
        "produce": produce,
        "inbound": inbound,
        "dispatch": dispatch,
        "expedite": expedite,
        "unmet": unmet,
        "served_cum": served_cum,
        "inventory": inventory,
        "quarantine": quarantine,
        "op_cost": op_cost,
        "eta": eta,
        "cvar_excess": cvar_excess,
        "amb_lam": amb_lam,
        "amb_gamma": amb_gamma,
        "amb_alpha": amb_alpha,
        "amb_beta": amb_beta,
    }

def build_model(data, time_limit):
    config = data["config"]
    items = data["items"]
    warehouses = data["warehouses"]
    suppliers = data["suppliers"]
    clinics = data["clinics"]
    periods = data["periods"]
    scenarios = data["scenarios"]
    supplier_item = data["supplier_item"]
    supplier_wh = data["supplier_wh"]
    wh_clinic = data["wh_clinic"]
    fleets = data["fleets"]

    model = Model("medical_supply_dro_response")
    model.setParam("display/verblevel", 0)
    model.setParam("limits/gap", 0.0005)
    model.setParam("limits/time", float(time_limit))

    y_open = {
        w: model.addVar(vtype="B", name=f"open[{w}]") for w in data["warehouse_ids"]
    }
    y_active = {
        s: model.addVar(vtype="B", name=f"active[{s}]") for s in data["supplier_ids"]
    }

    stock = {}
    for w in data["warehouse_ids"]:
        for item in data["item_ids"]:
            ub = items[item]["max_stock_per_warehouse"]
            if items[item]["cold_chain_required"] and not warehouses[w]["cold_chain"]:
                ub = 0.0
            stock[(w, item)] = model.addVar(lb=0.0, ub=ub, name=f"stock[{w},{item}]")

    reserve = {}
    for s in data["supplier_ids"]:
        for item in data["item_ids"]:
            ub = supplier_item[(s, item)]["max_reserved_capacity"]
            if items[item]["cold_chain_required"] and not suppliers[s]["cold_chain_certified"]:
                ub = 0.0
            reserve[(s, item)] = model.addVar(
                lb=0.0, ub=ub, name=f"reserve[{s},{item}]"
            )

    run = {}
    produce = {}
    for omega, period, s, item in data["prod_keys"]:
        max_cap = supplier_item[(s, item)]["max_reserved_capacity"]
        max_mult = data["supplier_avail_max"][s]
        run[(omega, period, s, item)] = model.addVar(
            vtype="B", name=f"run[{omega},{period},{s},{item}]"
        )
        produce[(omega, period, s, item)] = model.addVar(
            lb=0.0,
            ub=max_cap * max_mult,
            name=f"prod[{omega},{period},{s},{item}]",
        )

    inbound = {}
    for omega, period, s, w, item in data["inbound_keys"]:
        lane_cap = supplier_wh[(s, w)]["base_capacity"]
        ub = min(
            supplier_item[(s, item)]["max_reserved_capacity"] * data["supplier_avail_max"][s],
            lane_cap
            * data["supplier_lane_cap_max"][(s, w)]
            / max(items[item]["load_factor"], 1e-9),
        )
        inbound[(omega, period, s, w, item)] = model.addVar(
            lb=0.0,
            ub=ub,
            name=f"in[{omega},{period},{s},{w},{item}]",
        )
